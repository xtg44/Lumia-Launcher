# Lumia Launcher 后台更新方案

> 目标：**更新不再依赖浏览器** —— 应用内完成「检查 → 下载 → 校验 → **退出** → 替换 → 重启」
> 路线：**自研全自动**（不引入 Tauri 官方 updater）；macOS 更新包用 **zip**
> 核心前提：**替换发生在应用退出之后**，不做「运行中替换」
> 状态：**已实现**（P0~P2，macOS 闭环可用；Windows 分支已编译但未真机验证）· 最后更新：2026-10-02
> 实现位置：后端 `src-tauri/src/updater.rs` + `main.rs` 的 `self_update_prepare` / `self_update_apply`；
> 前端 `src/components/UpdateModal.vue` + 设置页两个开关
> 关联文档：[安卓端技术方案](./安卓端技术方案.md) · [前端开发指南](./前端开发指南.md)

## 一、结论摘要

| 问题 | 答案 |
|---|---|
| 技术上行不行？ | **行。** 而且比想象中简单——**应用退出后再替换**，任何平台都只是普通的文件操作 |
| 为什么要先退出？ | 退出后没有任何文件被占用，**不用处理文件锁、不用三段式腾位、不用「删不掉就下次再删」的补丁**，整包删掉重建即可 |
| 那要额外做什么？ | 只多一个**几行的独立小进程**（helper）：等主进程退出 → 替换 → 拉起新版。自己替换自己做不到，因为被替换的就是自己 |
| 为什么不用 Tauri 官方 updater？ | 三条硬约束：**签名密钥强制**（私钥丢失即永久失去更新能力）、**Windows 必须改成 NSIS/MSI 安装版**（丢掉免安装形态）、macOS 要 `.app.tar.gz` + 重建清单端点 |
| 最大成本在哪？ | 不在替换，在**失败回滚**与**平台差异**（权限、杀软、更新包格式） |
| 需要服务端配合吗？ | **需要。** macOS zip 的下载地址与校验哈希必须由官网 API 提供 → 这是唯一的阻塞项 |
| 现实工期 | 后端 2~3 天，前端 1 天，两端联调 + 失败场景测试 2 天 |

## 二、现成可复用的部分（这是本项目最大的优势）

| 能力 | 位置 | 复用方式 |
|---|---|---|
| 32 线程分段下载 + 3 次分块重试 + 进度事件 | `main.rs` `download_file`（7864 行起） | **直接复用**，一行不改 |
| 进度事件监听 | `src/utils/tauri.ts` `listenDownloadFileProgress` | 直接复用 |
| 下载进度条样式 | `App.vue` `.progress-bar` / SettingsView `.dl-progress-bar` | 照抄样式，不另造 |
| 应用重启 | `tauri 2.11.5` 的 `AppHandle::restart()`（`app.rs:588`） | **本方案不用它**：主进程已退出，重启由 helper 负责 |
| 进程派生 | `std::process::Command` + `Stdio::null()` + 脱离进程组 | 写 helper 用，标准库即可，不引依赖 |
| 打开外部链接 | `open_url` 命令（`open::that`） | 作为降级出口 |
| 网络客户端 | `reqwest`（已带 `stream`/`rustls-tls`/`system-proxy`） | 直接复用 |
| 更新信息结构 | `UpdateCheckResult`（`main.rs:8143`） | 扩展字段即可 |

> ⚠️ **不能复用**：`extract_zip_dir`（`main.rs:4675`）。它用 `fs::File::create` + `io::copy` 解压，**不保留 Unix 权限位、不处理符号链接**（见 4699~4700 行）。拿它解压 `.app` 会让主二进制丢掉 `+x`，app 直接启动不了。macOS 必须改用系统自带的 `ditto -x -k`。

## 三、关键前提与已验证事实

### 3.1 替换在进程退出之后进行 —— 不做「运行中替换」

最早设想过「应用还在跑着就把自己换掉」，还为此做了本机实验（假 bundle + 心跳法，结论：macOS 上确实能用「改名走 → 写新的 → 删旧的」三段式换掉运行中的 `.app`）。

**但这个方向被放弃了，因为它没有任何收益，只带来复杂度：**

| | 运行中替换 | **退出后替换（采用）** |
|---|---|---|
| 旧包怎么处理 | 只能改名腾位，不能 `rm -rf` | 直接删干净，不留残留 |
| 失败恢复 | 要自己管备份改名与回滚 | 换完再删备份，逻辑一样，但没有「文件被占用」这个变量 |
| Windows | 运行中的 exe 不能删/覆盖，只能改名，且删旧文件要拖到下次启动 | 退出后就是一个普通文件，`del`/`move` 随便用 |
| 杀软敏感度 | 「程序在运行中改写自己」是最容易被拦的行为 | 常规的文件替换行为 |
| 用户可感知 | 无 | **有**：会看到应用退出又起来，但这本来就是用户点的按钮 |

用户点的就是「更新」，那么退出、换文件、再起来 —— 这是最符合直觉、也最省事的路径。

> 附录（保留结论备查）：macOS 上运行中的 `.app` 确实可以改名和写入，进程不受影响；那段实验的价值在于顺带确认了 3.2 / 3.3 两条前提 —— 它们对新方案同样成立。

### 3.2 macOS：替换不需要 sudo ✅ 已确认

```
/Applications                     drwxrwxr-x  root:admin
/Applications/Lumia Launcher.app  drwxr-xr-x  xiaotiangua:admin
```

当前用户在 `admin` 组，且这份 app 的属主就是本人 → **普通权限即可替换**。
（若用户把 app 装在只读位置或 root 属主下，走降级路径，见第八节。）

### 3.3 未签名不影响自更新，反而更顺 ✅ 已确认

```
Signature=adhoc   TeamIdentifier=not set   Sealed Resources=none
```

- 现在**没有 bundle 级签名**（只有链接器自动打的 ad-hoc），所以不存在「替换导致签名失效」的问题
- `codesign --verify` 在**原始包上就报错**（`code has no resources but signature indicates they must be present`），非替换引起，两个包状态一致
- **额外收益**：应用自己下载的文件**不会被加 `com.apple.quarantine`** → 更新后首次启动**不会**弹「无法验证开发者」。这条路比让用户从浏览器下载**体验更好**

### 3.4 Windows：待验证（本机无 Windows 环境）

「运行中的 exe 不能删/覆盖」这个限制，在**退出后替换**的方案里**不再需要绕**（不需要那个「先把自己改名」的技巧）。Windows 侧剩下要真机确认的只有两点：

1. 分离出去的 helper 进程在父进程退出后是否继续存活（预期：存活）
2. 杀软（Defender / 第三方）对「应用自我替换」的反应 —— **这是 Windows 侧最大不确定性**

## 四、整体流程

```
                        ┌─────────────────────────┐
   启动时 / 手动点击 ──▶ │ check_for_updates (已有) │
                        └───────────┬─────────────┘
                                    │ has_update
                                    ▼
                        ┌─────────────────────────┐
                        │ 解析本机 platform+arch  │
                        │ 取对应更新包 URL+hash   │
                        └───────────┬─────────────┘
                                    ▼
                  ┌──────────────────────────────────┐
                  │ 后台下载到 updates/<ver>/        │ ← 复用 download_file
                  │ 进度事件 → 弹窗进度条            │
                  └───────────┬──────────────────────┘
                              ▼
                  ┌──────────────────────────────────┐
                  │ 校验 SHA-256 + 包结构 + 架构     │
                  │ 任一不过 → 丢弃 + 降级           │
                  └───────────┬──────────────────────┘
                              ▼
                  ┌──────────────────────────────────┐
                  │ 提示「已就绪，更新会关闭应用」   │ ← 用户掌控时机
                  └───────────┬──────────────────────┘
                              ▼ 用户点「立即更新并重启」
                  ┌──────────────────────────────────┐
                  │ 1) spawn 分离的 helper 进程      │
                  │ 2) 主进程立刻 exit               │ ← 进程一退，所有文件都没人占用
                  └───────────┬──────────────────────┘
                              ▼
                  ┌──────────────────────────────────┐
                  │ helper：等主进程退出             │
                  │  → 旧包改名备份                  │
                  │  → 新包就位                      │
                  │  → 成功则删备份 / 失败则回滚     │
                  │  → 拉起新版本                    │
                  └───────────┬──────────────────────┘
                              ▼
                  ┌──────────────────────────────────┐
                  │ 新版本启动：清理备份与下载缓存   │
                  └──────────────────────────────────┘
```

**关键设计决策：下载与校验全静默，但「退出 → 替换 → 重启」必须由用户点按钮触发。**

理由：用户很可能正在玩游戏、应用是**真的会退出再起来**，这个时机不能替他决定；而且万一失败，责任链也最清晰 —— 就是他点的那一下触发的。

## 五、macOS 实现细节

### 5.1 定位自身的 bundle

```
current_exe() → /Applications/Lumia Launcher.app/Contents/MacOS/lumia-launcher
                ↑ parent × 3 = .app bundle 路径
```

**必须先做安全闸门**，否则开发时会把自己编译目录搞坏：

| 检查 | 不通过的处置 |
|---|---|
| 路径以 `.app` 结尾且含 `/Contents/MacOS/` | 拒绝自动更新 → 降级为「打开安装包」 |
| 路径含 `/target/debug/` 或 `/target/release/`（dev / 未打包运行） | 同上（开发保护） |
| bundle 父目录可写 | 同上，并提示「需要手动安装」 |

### 5.2 更新包格式（macOS）

构建时额外产出一个 zip，顶层就是 `Lumia Launcher.app`：

```bash
ditto -c -k --sequesterRsrc --keepParent \
  "Lumia Launcher.app" \
  "LumiaLauncher_<version>_<arch>.zip"
```

解压**必须用 `ditto -x -k`**（系统自带）：

```bash
ditto -x -k "<pkg>.zip" "<临时目录>"
```

原因：`.app` 里有符号链接（Frameworks 版本链接）和可执行权限位，`zip` crate 的 `extract_zip_dir` 两者都不保留（见第二节）；`ditto` 是 macOS 原生工具，正确处理权限、xattr、符号链接。

### 5.3 替换脚本（在应用退出后执行）

helper 本体就是一段 `/bin/sh`。核心是：**等主进程死透 → 备份旧包 → 新包就位 → 成功删备份 / 失败搬回来 → 拉起新版**。

```sh
#!/bin/sh
set -u
PID="$1"           # 主进程 pid
TARGET="$2"        # /Applications/Lumia Launcher.app
STAGED="$3"        # 解压出来的新包路径

# 1) 等主进程退出（轮询上限 15s；超时也继续，此时文件其实已无占用）
i=0
while kill -0 "$PID" 2>/dev/null && [ "$i" -lt 75 ]; do sleep 0.2; i=$((i+1)); done

# 2) 备份旧包 —— 是 mv 不是 rm，第 3 步失败要能原样搬回
rm -rf "$TARGET.bak" 2>/dev/null
mv "$TARGET" "$TARGET.bak" || exit 10

# 3) 新包就位（ditto 保留权限位 / 符号链接 / xattr）
if ditto "$STAGED" "$TARGET"; then
  rm -rf "$TARGET.bak"                 # 4a) 成功：删备份
else
  rm -rf "$TARGET"
  mv "$TARGET.bak" "$TARGET"           # 4b) 失败：回滚
fi

open -n "$TARGET"                      # 5) 无论成败都把应用拉起来
rm -rf "$(dirname "$STAGED")"          # 6) 清理解压临时目录
```

要点：

- **用 `ditto` 而不是 `mv`**：用户可能把 app 装在另一个卷上，`mv` 会退化成拷贝；且只有 `ditto` 会正确处理 `.app` 内部的符号链接、可执行位与 xattr
- **非零退出码 + 让父进程写日志**：helper 脱离终端后看不到它的输出，失败原因要落盘才能排查（`exit 10` = 备份失败、`exit 11` = ditto 失败等）
- **`open -n` 用绝对路径**，不依赖工作目录

### 5.4 派发 helper（Rust 侧）

```rust
use std::process::{Command, Stdio};

let script = data_dir.join("updates/apply.sh");   // 提前写好并 chmod 0o755
Command::new("/bin/sh")
    .arg(&script)
    .arg(std::process::id().to_string())          // 脚本靠这个轮询本进程
    .arg(&bundle_path)
    .arg(&staged_path)
    .stdin(Stdio::null()).stdout(Stdio::null()).stderr(Stdio::null())
    .process_group(0)                             // 脱离进程组，不随父进程一起被回收
    .spawn()?;

app.exit(0);   // 立刻退出，之后的事都归 helper
```

三条纪律：

1. helper 必须在主进程退出**前**就 spawn 好，否则没人点火
2. 退出前**不要**再动下载目录 / 解压目录 —— helper 会处理，抢着删会打架
3. 退出走 `app.exit(0)` / `std::process::exit(0)` 的短路径，不要走任何会阻塞或弹确认的退出钩子

## 六、Windows 实现细节

### 6.1 定位自身

`current_exe()` 直接就是 exe 路径。因为发布物是**免安装裸 exe**，用户可能放在桌面、下载目录、D 盘任意位置 —— 必须以 `current_exe()` 为准，不能假设安装目录。

### 6.2 替换流程

```
1. 检查所在目录可写（试写临时文件后删除）
   └─ 不可写（Program Files 等）→ 降级为「打开安装包」
2. 下载新 exe → <dir>/lumia-launcher.new.exe
3. 校验 SHA-256 + PE 文件头
4. 把自身复制一份 → <dir>/lumia-helper.exe
5. spawn：lumia-helper.exe --apply-update --pid <本进程> --target <exe> --new <new.exe>（分离、无窗口）
6. 主进程立刻 exit
   ─────────────── 以上是应用还活着；以下是锁已释放 ───────────────
7. helper：
   a. 轮询直到 target exe 可被改名（说明 Windows 已释放文件锁）
   b. target 改名 lumia-launcher.old-<ts>.exe
   c. new.exe 改名 lumia-launcher.exe      ← 失败则把 .old 改回来
   d. 成功 → 删 .old
   e. 启动 lumia-launcher.exe
   f. 卸载自身：改名为 lumia-helper.old-<ts>.exe 后，交由主程序下次启动时删除
```

### 6.3 为什么 helper 是「自身副本」而不是一个 .bat

**不要生成 `.bat` / `.ps1` 来做替换。** 用户的安装路径可能是 `C:\Users\张三\桌面\` 这类**含非 ASCII 字符**的路径，而 `cmd` 的脚本文件读的是当前 ANSI 代码页 —— 中文路径在脚本里会变成乱码，`move` 直接找不到文件。这是本机在别处已经踩过的一类坑。

用自身 exe 副本做 helper 则完全绕开：路径通过 `Command::arg()` 以 UTF-16 传入，不经过任何 shell 解析，空格、中文、emoji 都无所谓。同时还顺带保证了 helper 一定能在目标机器上运行（它就是这台机器上正在跑的那个二进制）。

### 6.4 需要真机确认的两点

1. 分离出去的子进程在父进程退出后是否继续存活（预期：存活）
2. 杀软（Defender 及第三方）对「应用自我替换」的反应 —— **这是 Windows 侧最大不确定性**

## 七、安全设计

更新链路本质是「**从远端下载代码并执行**」，是攻击价值最高的路径，必须设防。

| 层 | 措施 |
|---|---|
| 传输 | 强制 HTTPS（现有 API 已是 https） |
| 完整性 | **SHA-256 校验**，哈希由 API 提供，不匹配立即删除并报错 |
| 格式 | 校验解压后的包结构完整（`.app/Contents/MacOS/lumia-launcher` 存在且可执行 / PE 头有效） |
| 架构 | 校验二进制架构与本机匹配（防止 x64 机器装了 arm64 包） |
| 位置 | 更新包只落在应用数据目录或 exe 同目录，不落 `/tmp` 等共享位置 |

**必须诚实说明的边界**：哈希来自同一个服务端，所以它能防「下载损坏 / 传输被篡改 / CDN 投毒」，**不能防「服务端本身被入侵」**。真正能防后者的只有代码签名（macOS 公证 + Windows Authenticode），那是另一件更重的事（需要 Apple Developer 账号 $99/年 + 代码签名证书）。

在「无签名 + 有哈希」这个档位上，安全性已经不弱于现状（现状是用户手动从浏览器下载同源的安装包）。

## 八、失败与降级矩阵

**原则：任何一步失败，都必须保证「应用还能用」，且给出明确出口。**

| 场景 | 检测方式 | 行为 |
|---|---|---|
| 非标准安装位置 / dev 运行 | 路径检查（5.1） | 不自动替换，改为「下载并打开安装包」 |
| 目标目录不可写 | 试写临时文件 | 同上，提示需要手动安装 |
| 下载失败 | reqwest 错误（已有 3 次分块重试） | 可重试；连续失败 → 官网链接 |
| SHA-256 不匹配 | 本地计算比对 | **删除文件**，报错，不安装，给官网链接 |
| 解压失败 / 结构不完整 | `ditto` 返回码 + 路径探测 | 报错 + 官网链接 |
| 架构不匹配 | 读二进制头 | 报错 + 官网链接 |
| helper 没能起来 | `spawn` 返回码 | **不退出**，报错并保留已下载的包，可重试 |
| 等主进程退出超时 | helper 轮询上限（15s） | 照常往下走（若进程真还在，改名会失败 → 落进回滚分支） |
| **替换中途失败** | helper 各步退出码 | 旧包**原样搬回**并拉起旧版；下次启动读日志告知用户 |
| 新版拉起后立刻崩溃 | 可选加固：helper 拉起后确认进程存活 | 回滚到备份，拉起旧版 |
| 备份清理失败 | `rm` 返回码 | 静默忽略，下次启动再清 |

## 九、前端交互

### 9.1 弹窗状态机

```
idle ──▶ checking ──▶ (无更新 → 关闭)
                 └──▶ available ──▶ downloading(%) ──▶ verifying
                                                        │
                        ┌───────────────────────────────┤
                        ▼                               ▼
                  ready(更新已就绪)                    error(原因 + 出口)
                        │
                        ▼ 点「立即更新并重启」
              spawning ──▶ exiting      ← 到这儿应用就关了，剩下的交给 helper
```

### 9.2 UI 要点

- 进度条**照抄** `SettingsView` 的 `.dl-progress-bar` / `.dl-progress-fill`（不另造样式）
- 已下载字节 / 总字节，复用现有 `format_bytes` 的输出格式
- `ready` 态文案必须把「会关闭应用」讲清楚：「新版本已下载完成，点击后应用会关闭并自动重启完成更新」+「稍后再说」按钮
- `error` 态必须给**两条出口**：「重试」和「打开官网下载」
- 所有交互沿用项目惯例：弹窗用 `<Transition name="modal">`（见 `UpdateModal` / `WhatsNewModal`），按钮沿用 `--button-bg` / `--button-active` 那套，**不引入 hover 上浮或新动效**

### 9.3 设置页新增项

| 项 | 默认 | 说明 |
|---|---|---|
| 自动检查更新 | 开 | 已有行为，补一个显式开关 |
| 自动下载更新 | 开 | 静默下载，包不大（6~19 MB） |
| 下载完成后自动重启 | **关** | 默认不打断用户，只在弹窗里提示 |

## 十一、需要官网 API 配合（**唯一阻塞项**）

现有接口 `GET https://lumialauncher.cn/api.php?action=version` 返回的是**安装包**地址（dmg / exe），自更新需要的是**更新包**地址 + 校验哈希。

> 📤 **对外沟通版本已单独整理**：`docs/官网更新接口对接说明.md` —— 自包含、可直接转发给官网对接人
> （含真实哈希、打包命令、自查清单、报错对照表）。本节保留设计视角。

### 方案 A（平铺 · 备选）

客户端**两种结构都支持**，服务端二选一即可（方案 B 优先解析）：

在现有 `version` 对象里平铺新增：

```json
{
  "version": {
    "latest": "v1.0 beta 2",
    "mac_arm64_zip": "https://.../LumiaLauncher_1.0.0-beta.2_arm64.zip",
    "mac_x64_zip":   "https://.../LumiaLauncher_1.0.0-beta.2_x64.zip",
    "win_zip":       "https://.../lumia-launcher.exe",
    "mac_arm64_zip_sha256": "02059e37...",
    "mac_x64_zip_sha256":   "50bf33e3...",
    "win_zip_sha256":       "74b23b78..."
  }
}
```

### 方案 B（结构化）—— ✅ **已采用**

新增一个 `update` 对象，按 `平台-架构` 索引：

```json
{
  "version": {
    "latest": "v1.0 beta 2",
    "update": {
      "macos-aarch64": { "url": "...", "sha256": "...", "size": 0 },
      "macos-x86_64":  { "url": "...", "sha256": "...", "size": 0 },
      "windows-x86_64":{ "url": "...", "sha256": "...", "size": 0 }
    }
  }
}
```

**为什么选 B 而不是 A**：A 的键名 `win_zip` 里放的其实是**裸 exe**（Windows 的更新物不是压缩包），
名实不符极易让对接人误解成「要打个 zip 上来」；B 的键名是标准平台三元组，`url/sha256/size` 自解释，零歧义。

**客户端必须做的兼容**：字段缺失 ≠ 出错。老服务端没有这些字段时，应**自动退回到现有行为**（打开浏览器下载），不弹错误。

> 已知接口里已有 `mac_arm64` / `mac_x64` 两个字段（当前客户端未使用）。自更新**必须按架构取包** —— arm64 机器装了 x64 包只能靠 Rosetta 勉强跑，反过来（x64 装 arm64）直接无法运行。
