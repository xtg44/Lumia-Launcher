# Lumia Launcher 内置更新 · 官网接口对接说明

> 收件人：负责 `lumialauncher.cn` 后端接口的同学
> 要做的事：在版本接口里**新增一个 `update` 对象**，里面放三个平台的更新包直链和 SHA-256。
> 改动量：一个接口加一段赋值。**不影响任何现有字段和现有功能。**
> 生效时机：**再下一个版本（beta 4）才真正被下载**（更新包只有「已带自更新能力、且版本更旧」的客户端会取）—— 可以先改好结构，择机填值，见 §4。

---

## 0. 背景（一句话）

启动器**即将支持应用内自动更新**：用户在弹窗里点「更新」，程序自己下载、校验、替换、重启，**不用再跳浏览器手动装**。
（该能力已开发完成并通过验证，**随下一个版本发布** —— 当前已发布的版本还没有它。）

这件事需要接口告诉客户端三件事：**从哪下、多大、校验值是多少**。

---

## 1. 接口现状

客户端请求：

```
GET https://lumialauncher.cn/api.php?action=version
```

当前返回（实测，2026-10-02）：

```json
{
  "ok": true,
  "version": {
    "beta": "v1.0 beta 2",
    "stable": null,
    "latest": "v1.0 beta 2",
    "channel": "beta",
    "beta_download": "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-Windows.exe",
    "win_download":  "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-Windows.exe",
    "mac_download":  "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-arm64.dmg",
    "mac_arm64":     "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-arm64.dmg",
    "mac_x64":       "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-x64.dmg",
```

## 2. 需要新增什么

在 `version` 对象里增加一个并列的 `update` 对象，三个平台各一项（下面示例中的 URL / 哈希**只是格式示范**，实际值何时填见 §4）：

```json
{
  "ok": true,
  "version": {
    "beta": "v1.0 beta 2",
    "stable": null,
    "latest": "v1.0 beta 2",
    "channel": "beta",
    "beta_download": "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-Windows.exe",
    "win_download":  "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-Windows.exe",
    "mac_download":  "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-arm64.dmg",
    "mac_arm64":     "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-arm64.dmg",
    "mac_x64":       "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-x64.dmg",
    "stable_download": null,

    "update": {
      "macos-aarch64": {
        "url": "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-arm64.zip",
        "sha256": "c104744299c0a2dde3476b60e3470d6378f321f2505a97f6692cc05f104ca147",
        "size": 6896185
      },
      "macos-x86_64": {
        "url": "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-MacOS-x64.zip",
        "sha256": "0762602b6922b79e58deffd521f3b23ec808c114bc1f05fca63ad9afdcbbc90a",
        "size": 7144377
      },
      "windows-x86_64": {
        "url": "https://lumialauncher.cn/download/Lumia-Launcher-1.0.0-beta.2-Windows.exe",
        "sha256": "74b23b7814ac8717b062599998696b7a500274f07c0115f639b414f32db375c6",
        "size": 19825152
      }
    }
  }
}
```

> ⚠️ **现在填了也不会被使用，先别填。** 应用内自更新是 `beta 3` 才引入的能力，而 **`beta 3` 自己的更新包同样没有消费者**
> —— 不存在「版本比它旧、却又已带自更新能力」的客户端。第一个真正会被下载的包是 `beta 4` 的。生效时机见 §4.1。
>
> 上面这组值就是 §4.2 的那组**预演数据**（用 beta 2 产物做的），摆在这里只是让你看清字段长什么样。

### 字段说明

| 键 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `update` | object | 是 | 三个平台各一个子键，**键名固定**：`macos-aarch64`（Apple 芯片）、`macos-x86_64`（Intel）、`windows-x86_64` |
| `update.<平台>.url` | string | 是 | 更新包**直链**，必须 `https://` 开头 |
| `update.<平台>.sha256` | string | 强烈建议 | 更新包的 SHA-256，**完整 64 位小写十六进制** |
| `update.<平台>.size` | number | 可选 | 字节数，用于显示下载总量 |

> 三个平台的键名必须**完全一致**（小写 + 连字符）。客户端按运行平台查表，键名不匹配就等于「没提供」。

## 3. 三条必须遵守的格式要求

### ⚠️ 3.1 版本号写法必须和客户端一致（最容易踩）

`latest` 字段**必须继续沿用现在的写法**：`v1.0 beta 2`、`v1.0 beta 3`……

客户端比较版本号的方式是**只抽取数字序列**再逐位比大小：

| `latest` 的写法 | 抽取结果 | 与当前版本 `v1.0 beta 2` → `[1,0,2]` 比较 |
|---|---|---|
| `v1.0 beta 3` | `[1,0,3]` | `[1,0,3] > [1,0,2]` → ✅ **判定有新版本** |
| `1.0.0-beta.3` | `[1,0,0,3]` | `[1,0,0,3] < [1,0,2]` → ❌ **判定没有新版本，更新永远不弹** |

**所以请不要顺手改成 semver 写法**（`1.0.0-beta.3`）。它是数字序列里多出来的一个 `0` 把比较带偏了。
发 beta 3 时 `latest` 就写 `v1.0 beta 3`。

### 3.2 `url` 必须 `https://` 开头

不是 `https://` 的地址会被客户端直接丢弃（等同于没填）。

### 3.3 `sha256` 必须是完整 64 位十六进制

不足 64 位、含非十六进制字符都会被丢弃 —— 丢弃后客户端**跳过校验、只靠 HTTPS 保护**（不报错，但也失去了防篡改能力）。所以请务必填对。

## 4. 更新包谁来提供 + 什么时候给

**更新包由我们（客户端侧）构建并提供，你们只需要上传 + 填字段。**

### 4.1 生效时机：`beta 4` 才开始被下载

一个关键前提：**版本 N 的更新包，只有「版本比 N 旧、且自身已带应用内自更新能力」的客户端会去下载。**
跑着版本 N 的客户端不会下载版本 N 自己的包（它已经是最新的了，`hasUpdate` 为 false）。

自更新是 `beta 3` 才引入的，套用上面的规则：

| 版本 | 上一版有自更新能力？ | 它的更新包有人下载吗？ |
|---|---|---|
| beta 2（现网） | 否（beta 1 没有） | 没有 |
| **beta 3** | 否（beta 2 **没有**该能力） | **没有** —— 不存在符合条件的客户端 |
| beta 4 | 是（beta 3 有） | **有** ← 第一个真正会被下载的包 |

所以：

- **`update` 字段现在填不填都不会被使用**，`beta 3` 发布时也一样 —— 没有任何已发布的客户端会读它
- 字段真正生效的时机是：**`beta 4` 发布时**，届时我们会把该版本的更新包与哈希一起给你
- 提前填还有一个**害处**：若 `beta 4` 时只改了 `latest` 忘了换 `update`，客户端会静默装回旧版（详见 §4.3）
- 所以这一节现在的作用是：**让你提前把接口结构改好**，等 `beta 4` 一发就能直接填上

### 4.2 一组真实数据（**仅用于核对格式，不要上传、不要填**）

下面这组是我们用 `beta 2` 的产物在本机做的**流程预演**。它的唯一用途是让你核对字段格式
（URL 长什么样、哈希多长、`size` 是字节还是 KB）：

| 平台 | 文件名 | 大小（字节） | SHA-256（64 位） |
|---|---|---|---|
| macOS Apple 芯片 | `Lumia-Launcher-1.0.0-beta.2-MacOS-arm64.zip` | 6896185 | `c104744299c0a2dde3476b60e3470d6378f321f2505a97f6692cc05f104ca147` |
| macOS Intel | `Lumia-Launcher-1.0.0-beta.2-MacOS-x64.zip` | 7144377 | `0762602b6922b79e58deffd521f3b23ec808c114bc1f05fca63ad9afdcbbc90a` |
| Windows | `Lumia-Launcher-1.0.0-beta.2-Windows.exe` | 19825152 | `74b23b7814ac8717b062599998696b7a500274f07c0115f639b414f32db375c6` |

> **为什么要先预演一遍**：确认「打包 → 算哈希 → 客户端解包安装」这条链路真的通
> （本机 16 项检查全过：能解开、顶层是 `.app`、有执行位、架构匹配、权限位正确）。
> 免得真发版那天才发现打包方式不对。
>
> 顺带一个交叉验证：上表 Windows 那一行的哈希，是我们把服务器上现有的包**只读下载回本地**实测得到的，
> 结果与本地构建产物一致 —— 说明现有的上传链路是可靠的。（全程只是 GET 下载到本地核对，**没有对服务器做任何改动**。）

### 4.3 ⚠️ 发新版时的硬约束：`latest` 和 `update` 必须同步改

客户端是「**先看 `latest` 判断有没有新版本，有更新才去 `update` 里取包下载**」。

所以如果只把 `latest` 升到新版本、而 `update` 里还留着旧包的地址，用户会被装上一个**旧版本**
—— 相当于版本回退，而且用户不会察觉。

**发版时这四样必须一起改**：`latest` + 每个平台的 `url` + `sha256` + `size`。

### 4.4 为什么 macOS 要单独传 `.zip`，不能直接用现有的 `.dmg`？

`.dmg` 是磁盘映像，程序无法自动挂载安装；`.zip` 里是 `.app` 本体，客户端能直接解压替换。

所以 `.dmg`（给人手动装）和 `.zip`（给程序自动更新）**两者并存、各有用途** ——
现有 `mac_arm64` / `mac_x64` 字段保持指向 `.dmg` 不变，更新包走独立的 `update` 字段。

## 5. 没加 / 加错会怎样（不会出事）

客户端做了**自动降级**，任何一个环节不满足都会**安静地退回现有行为**——弹窗显示「打开浏览器下载」，用户手动下载安装，流程照旧。

| 情况 | 用户看到什么 |
|---|---|
| `update` 字段完全没加 | 弹窗里是「打开浏览器下载」（和现在一样） |
| 只有 macOS 加了、Windows 没加 | macOS 用户能自动更新；Windows 用户走浏览器 —— **可以分批上** |
| `url` 不是 https / 键名拼错 / 格式不对 | 该平台退回浏览器下载，不报错、不崩溃 |
| `sha256` 填错（但格式合法） | 用户会看到「文件校验失败，请重试」——**这是唯一会让用户看到错误的情况**，所以填完请自查一遍 |

**因此等新版本发布后，也可以放心分步上线**：先只加 macOS 三项，验证没问题再加 Windows。

## 6. 发新版本时要做什么（三步）

以后每次发版，重复这三步即可：

**① 打包**（我们在 macOS 上执行）

```bash
cd "src-tauri/target/release/bundle/macos"
ditto -c -k --sequesterRsrc --keepParent "Lumia Launcher.app" \
      "Lumia-Launcher-<版本>-MacOS-arm64.zip"

cd "../../../x86_64-apple-darwin/release/bundle/macos"
ditto -c -k --sequesterRsrc --keepParent "Lumia Launcher.app" \
      "Lumia-Launcher-<版本>-MacOS-x64.zip"
```

> `--keepParent` 不能省：它保证 zip 里**顶层就是 `.app`**，否则客户端解压后找不到程序。
> 也不能用普通压缩工具替代 `ditto` —— 会丢掉可执行权限位，装上去打不开。

**② 算哈希**

```bash
shasum -a 256 Lumia-Launcher-<版本>-MacOS-arm64.zip
shasum -a 256 Lumia-Launcher-<版本>-MacOS-x64.zip
shasum -a 256 lumia-launcher.exe
```

**③ 上传 + 改接口**（⚠️ **四样必须一起改**）

把新版本的包传到 `download/`，然后同步更新：

- `latest` → 新版本号（如 `v1.0 beta 3`）
- `update.<平台>.url` → 新包的地址
- `update.<平台>.sha256` → 新包的哈希
- `update.<平台>.size` → 新包的字节数

> **只改 `latest` 不改 `update` 会造成版本回退** —— 用户会被装回旧版本且毫无察觉。见 §4.3。

## 7. 交付前自查清单

- [ ] `update` 三个键名拼写正确：`macos-aarch64` / `macos-x86_64` / `windows-x86_64`
- [ ] **`latest` 与 `update` 里指向的是同一个版本**（不能只升 `latest`，否则版本回退）
- [ ] 三个 `url` 都能在浏览器里直接下到文件（不是 404、不是跳转页）
- [ ] `url` 全部 `https://` 开头
- [ ] 每个 `sha256` 都是 64 位十六进制，且与文件**实际哈希一致**
- [ ] `size` 与文件实际字节数一致
- [ ] `latest` 是 `v1.0 beta N` 这种写法（**不是** `1.0.0-beta.N`）
- [ ] 两个 macOS zip 分别对应正确的架构（Apple 芯片的机器填 `macos-aarch64`，别填反）
- [ ] 现有字段（`mac_download` / `win_download` / `beta_download` / `mac_arm64` / `mac_x64` …）**一个都没删**

### 哈希核对命令（上传后在服务器上再跑一次）

```bash
shasum -a 256 Lumia-Launcher-<版本>-MacOS-arm64.zip
```

（§4.2 那组预演数据的 arm64 哈希是 `c1047442…` 开头，可用来确认命令本身没问题。）

## 8. 出问题时怎么对号入座

| 现象 | 原因 |
|---|---|
| 用户点了更新还是跳浏览器 | `update` 字段没加 / 键名拼错 / `url` 不是 `https://` |
| 一直不弹更新提示 | `latest` 写法不对（例如被写成了 `1.0.0-beta.3`），见 §3.1 |
| 提示「文件校验失败，可能与服务端描述不一致」 | `sha256` 填错，或文件上传后被重新压缩过 |
| 提示「更新包结构不完整」/「架构不符」 | macOS 的 zip 打包方式不对（漏了 `--keepParent`），或两个架构填反了 |
| 提示「更新包里没有找到 .app」 | zip 顶层不是 `.app`，同上 |
| 下载很慢或中断 | 下载源不支持断点续传（客户端会自动回退单线程重试） |

## 附：客户端解析逻辑摘要（便于你们核对）

```
1. GET api.php?action=version
2. 取 version.latest，与当前版本比数字序列 → 判断有没有新版本
3. 有更新时，按运行平台在 version.update 里取对应的一项
      Apple 芯片 → macos-aarch64
      Intel     → macos-x86_64
      Windows   → windows-x86_64
4. 拿到 url / sha256 / size 后：
      下载 → 比对 SHA-256 → 解压（macOS 用 ditto）→ 校验程序架构与可执行权限
      → 全部通过才提示用户「重启完成更新」
5. 任何一步不满足（字段缺失、格式不对、校验失败）→ 退回「打开浏览器下载」
```

有疑问随时找我这边确认，接口改完可以先只加 macOS 跑一轮验证。
