## 〇、使用边界（先读这一节）

本笔记是 **clean-room 参考**的产物，规则只有两条：

1. **只记录「机制 / 结构 / 接口形态 / 工程量 / 硬约束」，不搬运实现。**
   全文不出现任何源片段。出现的类名、符号名、常量名、文件路径都属于「事实」，用来说明"这里有个什么东西、它负责什么"，而不是可复制的实现。
2. **许可证红线不放宽。**
   FCL 与 ZalithLauncher2 均为 **GPL-3.0**。参考它们的设计思路不构成派生；但只要复制其代码（哪怕几行），整个 Android 端就必须转 GPL-3.0，已定的 MIT 直接作废。Amethyst-Android（LGPL-3.0）同理：**它的编排代码也不能抄进 MIT 仓库**，只能作为"该做什么"的清单。

> 判断口诀：**知道"要做什么、为什么必须做、不做会怎样"是合法的；拿到"具体怎么写"并粘贴过来就越线了。** 每实现一个模块前，先在此文档写下接口与流程，再自己写代码——不要边看参考源码边写。

## 二、FCL：模块与代码规模

顶层是 Gradle 多模块工程（`FoldCraftLauncher-main/settings.gradle.kts:15-29`）：`:FCL`（主 App）、`:LWJGL`（含 `3.3.3` / `3.4.1` 两个子模块）、`:ZipFileSystem`、`:Terracotta`。

| 模块 | 文件数 | 行数 | 说明 |
|---|---|---|---|
| `FCL/src/main/java` | 1029 | ~154.7k | `fclcore` 648 文件/87.8k 行 · `fcl` 219/43.6k · `fcllibrary` 83/10.6k · `fclauncher` 14/3.0k |
| `FCL/src/main/jni` | 39 | ~19.3k（**去掉 3 个 GL 头文件后仅约 4.1k**） | 引擎原生层，真正的"硬骨头" |
| `LWJGL/` | 88 | ~31.1k | 大部分是生成的 `GLCapabilities` |
| `ZipFileSystem/` | 15 | ~5.6k | OpenJDK zipfs 移植 |
| `FCL/src/main/jreAssets` | 23 个压缩包 | **154 MB** | 4 套 JRE（8/17/21/25） |

Java 侧四个包族的分工（`FCL/src/main/java/`）：`com/tungsten/fclcore`（启动器核心逻辑：版本解算、下载、启动参数）、`com/tungsten/fcl`（App 业务层：Activity/Fragment/游戏界面）、`com/tungsten/fclauncher`（**引擎编排层**，14 个文件，本次重点）、`com/tungsten/fcllibrary`（UI 组件库）。

> **关键情报**：真正的引擎编排层只有 **14 个文件约 3 千行**，原生层约 4 千行（不含 GL 头）。也就是说「引擎本体」并不庞大——庞大的是外围生态（MoD/整合包/联机/多语言 UI）。这对工期估算是好消息。

### 3.2 `com/tungsten/fclauncher/` 的职责切分（14 个文件）

- **`FCLauncher`** —— 启动主控。环境变量拼装（通用 / 模组加载器 / 渲染器 / 自定义四类）、JRE 的 `dlopen` 顺序、渲染器与 OpenAL 的加载、启动参数里占位符（`${natives_directory}`、`${gl_lib_name}` 等）的替换、以及日志脱敏（`--accessToken` 打码）。
- **`FCLConfig`**（Kotlin data class）—— 启动配置载体：context / javaPath / workingDir / renderer / args + lwjgl 版本 + 已装加载器标志。
- **`bridge/FCLBridge`** —— JNI 桥。静态块加载两个 so；native 方法面包括 `dlopen`、`setenv`、`chdir`、`setLdLibraryPath`、`redirectStdio`、`setupExitTrap`、AWT 屏幕帧渲染、数据注入、窗口移动。
- **`bridge/FCLBridgeCallback`** —— 日志 / 退出 / 光标模式的回调接口（native → Java）。
- **`utils/FCLPath`** —— 所有运行时路径的**单一事实来源**，集中注册并建目录。这个做法值得直接学：路径散落是 Android 端最常见的自伤。
- **`utils/Architecture`** —— 设备架构判定与架构字符串/整数互转。
- **`keycodes/*`** —— 键码映射全家桶（详见第六节）。
- **`CriticalNativeTest`** —— 仅用于探测 ART 是否支持 `@CriticalNative`（决定用哪张 JNI 方法表）。

### 3.3 我们（Lumia 安卓端）必须自己实现的步骤清单

按依赖顺序，这就是 ①-B 的最小任务分解：

1. 实例解算：版本继承合并、库与资源完整性校验
2. 启动参数生成：占位符替换表（`${classpath}` / `${natives_directory}` / 认证字段 / 资源字段）
3. 认证：微软设备码 / 离线，产出统一的账号信息（**`auth.rs` 可复用**）
4. Java 运行时选择：MC 版本 → Java 主版本映射
5. JRE 资产解包与补丁
6. 环境变量组装（`LD_LIBRARY_PATH` / `JAVA_HOME` / `TMPDIR` / 渲染器相关）
7. 多进程结构（主进程 + 下载服务进程 + 崩溃上报进程）
8. `dlopen` JRE 全套 so 与 `libjli.so`
9. `Surface` / `TextureView` 与 `ANativeWindow` 绑定
10. **JVM 进程内启动**
11. **图形上下文桥接**
12. **输入注入到 GLFW 回调**
13. 日志重定向与退出码捕获
14. AWT 假实现与引导

第 10~14 项是"必须懂、但单点并不大"的；真正的难点集中在第十三节评为 4~5 星的那几块。

## 四、JVM 进程内启动（★难度 2/5，坑在信号）

**机制**：Java 侧入口是 `com.oracle.dalvik.VMLauncher.launchJVM(String[])`（`FCL/src/main/java/com/oracle/dalvik/VMLauncher.java:6`），JNI 实现在 `FCL/src/main/jni/jre_launcher.c:207`。

关键在于**它没有直接调 `JNI_CreateJavaVM`**，而是走了 JDK 自带启动器的路：

1. `dlopen("libjli.so", RTLD_LAZY | RTLD_GLOBAL)`（`:123`）
2. `dlsym` 取 `JLI_Launch`（`:148`）
3. 按 `JLI_Launch` 的签名把**完整命令行**透传进去（`:160`）

这与桌面 `java -cp ... Main` **完全等价**——JLI 内部自己负责加载 `libjvm.so`、建 VM、解析 classpath、找 main。classpath 与主类**不在这里传**，而是在 Java 侧被拼进命令行（`DefaultLauncher.java:257-258`，主类紧跟在包装类之后）。

**两个必须照做的硬约束**：

- **调 `JLI_Launch` 之前要重置整个信号表**（`SIGHUP` 到 `NSIG`），其中 `SIGSEGV` 要用"忽略"而不是默认处理，否则会被 Android 的检查拦下（`jre_launcher.c:128-136`）。
- **要自己捕获致命退出**：给 `SIGABRT` 装处理函数 → 写管道 → 另一个线程据此走正常退出路径（`:72-120`），把 JVM 崩溃转成用户可见的退出码，而不是进程被静默杀掉。

`com/oracle/dalvik/` 这个包名不是随便起的：它是沿用 Boardwalk/Pojav 的 ABI 约定，让 native 端能按固定符号名绑定，**包内除声明外没有任何逻辑**。

> 自研提示：这块代码量极小（约 200 行 C），难点是信号处理与"退出码要能让用户看见"。放早期做，风险低、确定性高。

## 五、JRE 分发与装配（★难度 2/5，坑在细节）

### 5.1 分包形态（实测）

`FCL/src/main/jreAssets/app_runtime/java/` 下四套 JRE，每套 5~6 个文件：

| 文件 | 作用 |
|---|---|
| `universal.tar.xz` | 跨架构共用的部分（jar / 模块 / 字体等） |
| `bin-<arch>.tar.xz` | 架构相关部分，arch ∈ `arm` / `arm64` / `x86` / `x86_64` |
| `version` | 版本戳，**内容是纯数字**（如 `12` / `11` / `2`） |

实测体积（MB）：jre8 ≈ 23、jre17 ≈ 37、jre21 ≈ 46、jre25 ≈ 41（合计约 147 MB，与文档早先的 154 MB 一致）。
注意 **jre25 没有 `bin-x86.tar.xz`**——32 位 x86 只能跑 8/17/21。

### 5.2 装配流程要点（`FCL/src/main/java/com/tungsten/fcl/util/RuntimeUtils.java`）

- 版本比对靠 `version` 文件内容（`:46`）；不一致就**整目录删掉重装**。
- 顺序：先解 `universal.tar.xz`，再解 `bin-<设备架构>.tar.xz`（`:96-116`）。
- **必须能创建符号链接**：JRE 内部大量用软链，解包时要还原（`:195-201`）。解到不支持 symlink 的分区上会直接炸——这是选安装目录的前提条件。
- 小文件写入时插入极短延时（`Thread.sleep(25)`，`:187`），规避部分设备的 IO 抖动。
- 解压后立刻打补丁（`:222`）：`libfreetype.so.6` → `libfreetype.so` 改名；**把自带的 `libawt_xawt.so` 覆盖进 JRE**（`:240-242`，即第八节的假实现注入点）；再处理 `libunpack200.so`。

### 5.3 多版本共存与选择

- 目录固定四份：`<运行时目录>/java/jre{8,17,21,25}`。
- 选择逻辑：扫描每个含 `release` 文件的目录，从 `release` 里正则抽 `JAVA_VERSION`；匹配策略是**"精确匹配，否则取最小的、大于目标的版本"**（`FCL/src/main/java/com/mio/JavaManager.kt:72`）。
- 另有强制规则：新版本 MC 需要 Java 25，否则用 21（`LauncherHelper.java:529-534`）。
- Java 8 的判别方式很实用：**"存在 `jre/` 子目录且存在 `bin/javac`"**（`FCLauncher.java:528`），因为 JDK 8 与 9+ 的目录布局不同。

> 自研提示：这套东西没有任何"算法"，全是清单与细节。真正要提前决定的是 **JRE 从哪来**（自建 vs 用上游 AngelAuraMC 构建）与 **安装目录选哪**（必须支持 symlink）。

## 六、图形栈：多后端桥接（★难度 5/5 · 最难）

### 6.1 支持的后端矩阵

选择入口是环境变量 `POJAV_RENDERER`，在 `FCL/src/main/jni/egl_bridge.c:232-282` 里派发：

| 后端 | 取值意图 | 走哪张桥表 | 备注 |
|---|---|---|---|
| GL4ES / NG-GL4ES / VGPU | `opengles*` | GL 桥 | EGL + GLES，符号动态加载 |
| ANGLE | — | 借 GL 桥 | 换 `libEGL_angle.so` + `libGLESv2_angle.so` 即切换（`FCLauncher.java:288-298`） |
| VirGL | `gallium_virgl` | **不走桥表**，直接分支调用 | 需 `virgl_test_server` 配合 |
| Zink | `vulkan_zink` / `..._zink_kopper` | OSM 桥 | Mesa `GALLIUM_DRIVER=zink` |
| Freedreno | `gallium_freedreno` | OSM 桥 | 额外设 `MESA_LOADER_DRIVER_OVERRIDE=kgsl` |
| 自定义 Gallium | `custom_gallium` | OSM 桥 | 供插件渲染器 |
| 纯 Vulkan | `GLFW_NO_API` | 无上下文 | 直接把窗口句柄返回 |
| OSMesa 软渲染 | — | OSM 桥 | 兜底方案，`libOSMesa_8.so` / `libOSMesa_81.so` |

### 6.2 桥接层的抽象形态

**不是 C++ 虚表，而是一组全局函数指针 + 两个装配函数**（`FCL/src/main/jni/ctxbridges/bridge_tbl.h:12-35`）。指针集合就是 7 项能力：

1. 初始化后端
2. 创建上下文（支持共享）
3. 切换当前上下文
4. 取当前上下文
5. 呈现（swap buffers）
6. 处理表面变更/重建
7. 设置垂直同步

通用句柄结构只含"状态位 + 当前 `ANativeWindow` + 新 `ANativeWindow`"（`ctxbridges/common.h:11`），各后端在自己的结构体里**前置相同字段**，从而能复用同一套指针类型。

> 这套设计的可取之处：**把"窗口/表面生命周期"与"GL 后端"彻底解耦**，后端只关心上下文与呈现。自研时值得照这个形状走（函数表 + 共同首部），但要自己定义接口与命名。

### 6.3 `egl_bridge.c` 与 `environ`

- `egl_bridge.c` 是**对外入口 + 派发层**：初始化（挂 JNIEnv、acquire Surface、设置缓冲几何、上报屏幕尺寸）、按窗口提示决定 Vulkan 或 GL、创建/切换/呈现上下文、加载 Vulkan、FPS 统计，以及窗口桥的 JNI 实现。它内部含渲染器常量与 Adreno 设备探测。
- **`environ/environ.c` 的设计非常值得学**：它把一份全局单例通过**环境变量存指针**、在库的构造函数里"有则取、无则建"（`:13-27`）。原因是同一进程里 Dalvik 侧、JRE 侧、以及多个 `so` 各有独立的全局变量区——**跨 `dlopen` 边界共享状态只能靠环境变量或固定符号**。这份单例里装着：渲染后端选择、强制垂直同步、事件环形缓冲、光标坐标、9 个 GLFW 回调函数指针、两套 `JavaVM*`/`JNIEnv*`（Dalvik 与 JRE 各一套，另有渲染线程专用）、按键与鼠标按下状态的直写缓冲指针、窗口协商状态与就绪标志。

> 这块是我们自研的**最大风险点**：多后端互操作 + Surface 生命周期竞态。建议第一版只做 **GL4ES + OSMesa 两个后端**（一个能用、一个兜底），把其余后端留成接口位。

## 七、输入桥与虚拟按键（★难度 3.5/5）

### 7.1 跨 JVM 通道的设计

`FCL/src/main/jni/input_bridge_v3.c` 定义了一条"**Dalvik 侧只投递、JRE 侧只泵出**"的通道，两种消费模式：

- **队列模式**：事件先压进环形队列，由 JRE 侧在每帧 `glfwPollEvents` 的时机统一派发（`sendData:282` 写入；`pojavPumpEvents:148` / start/stop pumping 控制）。
- **直调模式**：直接同步调用 GLFW 回调，少一帧延迟。

用哪种由启动时决定（看目标版本是否带某个参数，`LauncherHelper.java:245`）——**这是个纯性能/兼容权衡的开关，自研时也需要一个**。

### 7.2 注入目标与事件编码

事件**不碰 MC**，而是注入到 `org.lwjgl.glfw.GLFW` 注册的 GLFW 回调（字符 / 光标进入 / 光标位置 / 按键 / 鼠标键 / 滚轮 / 窗口尺寸）。回调地址通过一组 `glfwSet*Callback` 的 JNI 实现在启动时从 Java 侧"登记"回 native（`:109-134`）。

事件类型用 1000 起的整数编码（`:26-31`）。JNI 方法用显式注册（而非按名查找），并在启动时探测 ART 是否支持 `@CriticalNative`，从而在两张方法表之间选（`:599-666`）——**漏掉这个探测会按机型崩**。

### 7.3 光标与虚拟鼠标

`glfwGetCursorPos` / `glfwSetCursorPos` 被本地实现，坐标存在全局单例里（`:241-279`）。抓取状态变化会回调 Dalvik 侧，再由 Java 通知游戏菜单显示/隐藏虚拟光标；Java 侧另有专门的 `CursorView` 负责贴图与偏移。

### 7.4 与虚拟按键系统的对接

Java 侧 `com/tungsten/fcl/control/` 是一整套可配置的虚拟控件系统：

- **数据层**：按键布局里每个按钮带 press / longPress / click / doubleClick 四类事件，每个事件可带输出键码列表、输出文本、是否持续按住、是否打开菜单、是否切换触控/鼠标模式、绑定哪个视图组。
- **视图层**：按钮、方向键、视图管理器、触控板等。
- **出口**：控件触发 → 遍历输出键码 → 转成启动器内部键码 → 经键码映射表转成 GLFW 键码 → 桥的 `sendKey` → native → GLFW 按键回调。鼠标键单独映射（左/中/右/滚轮）。
- **手柄**：摇杆被编码进高位序列，经手柄键码映射接入同一出口。
- **文字输入**：GL 模式与 AWT 模式各有一套字符发送策略。

**`keycodes` 包的分工**（这套分层值得照搬）：Android `KeyEvent` → 启动器内部键码 → GLFW 键码，中间还夹着一层"MC 按键绑定名 ↔ GLFW 键码"的映射。**三层分开的好处**：Android 侧换 API、GLFW 侧换版本、MC 侧改绑定名，各自只动一层。

## 八、JVM 层三个 hooks（★难度 3/5 · 单点小、知识密集）

三者都在 native 库加载时、检测到"这是第二个 VM（JRE 侧）"后安装（`input_bridge_v3.c:56-64`）。手段统一是**重注册 Java native 方法**（Java 方法名不变，native 实现被换掉），**不做字节码改写**。

| Hook | 不 hook 会怎样 | 换掉的目标 |
|---|---|---|
| `lwjgl_dlopen_hook` | LWJGL 用普通 `dlopen` 加载 `libvulkan.so`：① 无法换成自带驱动策略；② Android 10- 链接器命名空间不嵌套，从 native 目录外加载依赖会失败 | LWJGL 的 `DynamicLinkLoader.ndlopen`：遇到 `libvulkan.so` 返回自己的加载结果，遇到插件路径且设了句柄时直接返回，其余透传 |
| `java_exec_hooks` | `Runtime.exec("xdg-open", ...)` 在 Android 上必然失败（没有 `xdg-open`）；`ffmpeg` 因"只能执行以 `lib*.so` 命名的文件"而调用失败 | JDK 的进程创建入口（旧 JDK 与新版类名不同，需探测）：`xdg-open` 转成剪贴板/打开链接的回调；`ffmpeg` 换路径并重写子进程环境变量 |
| `emui_iterator_fix_hook` | 华为旧 EMUI 固件上，LWJGL 在遍历程序头的回调里做 `dlopen`，会**死锁整个链接器** | LWJGL 的 `SharedLibraryUtil.getLibraryPath`，直接返回失败让上层提前退出；仅在特定环境变量存在时安装 |

> 自研提示：这三个都是"**知道了就 100 行、不知道就查三天**"的类型。它们对应三个具体的外部行为假设（Vulkan 加载策略 / 子进程能力 / 厂商固件缺陷）。自研版本不必照抄这三个，但必须回答同样的三个问题。

## 九、驱动与链接器绕行（★难度 5/5 · 最硬）

**为什么要绕**：Android 从 N 起把动态库按命名空间隔离，应用默认命名空间只允许自身 native 目录与少量系统路径。GPU 驱动（如 Turnip）放在应用私有目录，直接 `dlopen` 会失败；而系统 `libvulkan.so` 已存在于默认命名空间，无法被"替换"。**这套逻辑只在 arm64-v8a 编译**（`CMakeLists.txt:18-20`，`nsbypass.c` 的实现整体被条件编译包住）。

| 模块 | 解决什么 | 机制要点 |
|---|---|---|
| `nsbypass` | 在应用进程里**自建私有命名空间**并把驱动目录纳入搜索路径 | 先用"扫描 `dlopen` 机器码找立即数"的技巧拿到加载器内部地址，再用加载器内部符号创建/连接命名空间，最后用带命名空间标志的扩展 `dlopen` 加载驱动 |
| `nsbypass`（去重） | 同一个 `libvulkan.so` 既要给系统用、又要换成私有驱动（SONAME 冲突） | 把真实 `.so` 复制到临时 fd，**就地改写 ELF 里的 SONAME 字段**为递增编号，再以"库 fd"方式加载 |
| `driver_helper/hook.c` → `linkerhook` | 让**驱动内部**对其他系统库的加载调用也被正确重定向；并兼容旧系统缺失的追踪符号 | 导出**同名强符号**拦截加载入口；由驱动侧把三个关键函数指针交给它。CMake 里强制 `-z global`（`CMakeLists.txt:53-57`），否则驱动解析不到被拦截的符号 |
| ByteHook 的角色 | 不是用于驱动加载，而是用于 **exit 拦截**与库自身的 PLT 级 hook 基建（MIT 许可，可用） | 通过 prefab 引入，CMake 里 `find_package` 必需（`CMakeLists.txt:10`） |

> **给自研的结论**：这块是整个 ①-B 路线的**最大未知数**，且与我们的目标不冲突——如果 M0 证明"系统自带驱动 + ANGLE/GL4ES 就够用"，就**根本不需要**这套绕行，可以整块砍掉。反之若必须上 Turnip/Zink，这就是硬骨头。**建议把"是否需要私有驱动"作为 M0 的一个明确验收项。**

## 十、AWT 占位与 Cacio（★难度 2/5 · 知识型）

**为什么可以用空库**：MC 与模组加载器只把 AWT 用于少数场景（启动器弹窗、字体、个别模组的 Swing 界面），而这里**把 AWT 后端整体换成了 Cacio/CTC**（纯 Java 的自定义图形环境）。因此对 JDK 原生 X11/headless AWT 的 native 实现没有真实需求——**只要符号齐全、不抛链接错误即可**。

- `jni/awt_headless/placeholder.c`：整个文件只有一行注释，产出空 `libawt_headless.so` 占位。
- `jni/awt_xawt/xawt_fake.c`：提供一批空实现，关键是把 **GTK 探测全部返回"没有"**（使 JDK 走纯 Java 字体与工具路径）。
- **如何被引导过去**：装配 JRE 时用自带的 `libawt_xawt.so` **覆盖** JRE 里的同名库（`RuntimeUtils.java:240-242`），同时换掉 `libawt_headless.so`。
- **Cacio 侧**：JVM 参数里把 `awt.toolkit` 与 `java.awt.graphicsenv` 指向 CTC 实现（Java 8 与 17 的包名不同），并用 bootclasspath / `--add-opens` 打开 `java.desktop` 内部包；Java 17 走 javaagent 方式。
- **AWT 模式的数据通路**：由 `awt_bridge.c`（单独编译成一个 so）实现屏幕帧拉取（整屏像素数组）、输入注入、窗口移动、剪贴板双向；当目标不是游戏（没有 gameDir，例如安装器）时，启动一个线程把像素画到 `Surface`。

> 自研提示：这是一整块"**如果你不知道就会卡死、知道了就只是照单配置**"的工作。第一版可以**先不做 AWT**：只支持"启动游戏"，不支持 MC 自带安装器/Swing 界面，能省掉一大块。

## 十一、LWJGL 补丁面（★难度 4/5）

### 11.1 三个模块的关系

| 模块 | 角色 | 关键点 |
|---|---|---|
| `LWJGL/compileOnly` | 编译期依赖 | 只为字节码生成所需的 ASM |
| `LWJGL/3.3.3` | 产出 3.3.3 的 Android 版 jar | 必须用 **Java 8 工具链**；把官方模块除排除清单外**合并**成一个 jar，排除项单独拷贝；产物直接写进 App 的 assets |
| `LWJGL/3.4.1` | 同上，3.4.1 | 必须用 **Java 17 工具链**；排除清单不同 |

> 注意这对工具链的要求：**上游 jar 以 Java 8 字节码发布，用高版本工具链产出会 class version 不匹配。** 自研时如果沿用官方 jar 做补丁，这条必须遵守。

### 11.2 需要改哪些点（按功能分类）

1. **窗口系统**：把原生 GLFW 换成**纯 Java 伪造的窗口系统**——`glfwInit` 等函数不再调原生库，而是绑定到引擎导出的入口（初始化、创建上下文、切换、呈现、垂直同步、事件泵、屏幕尺寸变更、 framebuffer 尺寸回调等）。
2. **上下文创建**：GLFW 的初始化 / 创建上下文 / 设为当前 / 呈现 / 垂直同步，全部转向平台无关的自绘后端。
3. **回调桥**：新增回调桥类，并把一组"设置回调"的 native 实现改为"把 Java 回调地址登记到 native"。
4. **平台扩展类降级**：所有平台专属的原生绑定类（EGL / OSMesa / X11 / Wayland / Win32 / Cocoa）统一改成"调用即抛未实现"。
5. **GL 能力初始化**：在生成的能力类里插入一个钩子，识别渲染器库名并做对应初始化（例如为 GL4ES 注册 framebuffer 尺寸回调）。
6. **类路径补充**：让引擎的 so 被当作 GLFW 库名加载，并通过 JVM 参数覆盖 LWJGL 的原生库名查找。
7. **打包侧**：jar 需要按"核心优先"合并重排，并排除 AWT 相关包。

另外，伪造的 GLFW 里**内联了一份 Android 的 `ArrayMap`**——因为 JRE 里没有 Android 的类。这类"搬运 Android 类进 JRE"的需求，自研时还会以别的形式出现。

## 十二、ZipFileSystem 模块（★难度 1/5）

**解决什么**：MC 生态（Forge/ModLauncher、Fabric、以及 HMCL 系工具）大量使用 `jar:` 虚拟文件系统来**不解压就读改 jar 内容**。该能力由 JDK 的 `jdk.zipfs` 模块提供，而 **Android 运行时的 libcore/ART 不含这个模块**，直接调用会报"找不到 provider"。

**做法**：把 OpenJDK 的 `com.sun.nio.zipfs` 全套（15 个文件约 5.6k 行）作为 Android library 打进 APK，并通过服务注册文件注册 provider。

> 注意：它服务的是**启动器进程**（Dalvik 侧），不是被启动的 JVM；被启动的 JVM 自己有完整的 JDK，不需要这个。

## 十五、踩坑清单（不做就会炸）

### 15.1 构建工具链

| 约束 | 值 | 不满足会怎样 |
|---|---|---|
| NDK 版本 | **27.0.12077973**（固定） | 版本相关的加载器符号行为会变，链接失败或运行期找不到符号 |
| compileSdk / minSdk / targetSdk | 35 / **26** / 34 | minSdk 26 是部分 desugaring 与文件系统 API 的下限 |
| Java 级别 | 17；但 **LWJGL 3.3.3 子模块必须用 JDK 8、3.4.1 用 JDK 17** | class version 不匹配 |
| R8 版本 | 需手动覆盖（Kotlin 2.4 超出 AGP 捆绑 R8 的支持范围） | dex 阶段崩溃 |
| ByteHook | 必须 prefab 可见（CMake `find_package` + Gradle 依赖 + `prefab=true`） | CMake 配置阶段直接失败 |
| linkerhook | 必须 `-z global` | 驱动解析不到被拦截的符号 |
| STL | `c++_shared` | 与预编译 so 的 STL ABI 不一致 |
| 模块名 | **不能以数字开头** | IDE/AGP 无法解析依赖（需重定向目录） |
| JRE 资产 | 不能直接放默认 assets 目录，需声明为生成源并**显式声明架构输入** | 切架构时残留旧架构 JRE，APK 巨大 |
| so 打包 | `useLegacyPackaging = true` | so 被非页面对齐压缩，`dlopen` 出问题 |
| so 合并 | 需 `pickFirsts` 收敛重复的 ByteHook | 合并失败 |

### 15.2 ABI 与平台差异

- **只有 arm64-v8a** 才定义 Adreno 相关宏、才链接 EGL/GLESv2；**命名空间绕行逻辑整体是 arm64 专属**，非 arm64 直接返回失败。
- ELF 处理**硬编码 64 位结构**——只支持 64 位。
- Vulkan 私有驱动路径要求 **Android 9（API 28）以上**。
- 表面切换处有"Android 已替我们释放过 surface 时不能再释放，否则 SIGSEGV"的规避——**这是 Surface 生命周期竞态的实证**，自研时必然遇到。
- **32 位设备必须补 `-Xss 1m`**，否则 MC 1.13+ 直接栈溢出。

### 15.3 系统与合规

- 用了全盘存储权限（`MANAGE_EXTERNAL_STORAGE` 及旧版开关）。**Google Play 高度限制**，同类应用普遍走官网/GitHub/F-Droid 分发。
- 必须关闭 native 堆指针标记（`allowNativeHeapPointerTagging="false"`），否则与 hook 的机器码扫描冲突。
- 用了大堆、独立下载进程、独立崩溃进程、VPN 服务（联机）等，均需在隐私与合规层面单独说明。

### 15.4 运行时

- 进 JVM 前必须重置信号表（`SIGSEGV` 用忽略）——否则被 Android 拦下。
- 退出码捕获两条路：hook `exit` 成功则用 hook，否则退化为 `atexit`；且需防重入。
- 设置 `LD_LIBRARY_PATH` 依赖加载器的**隐藏符号**，不同 Android 版本符号名不同，必须双查。
- `@CriticalNative` 支持性探测漏掉会按机型崩。
- **`dlopen` 顺序敏感**：`libjli` → `libjvm` → 基础库（freetype/verify/java/net/nio/awt/awt_headless/fontmanager）→ 最后递归补齐 JRE 下所有 so；退出陷阱必须早于启动 JVM。
- JRE 资产的 `version` 文件解析失败会抛数字格式异常。
- 解包必须能建软链，否则 JRE 大面积失效。

| `CardGrid` | 自研 | 卡片网格布局引擎（推箱式让位、拖拽挤压），**带单测** |
| `ColorPicker` | 自研 | HSV 取色器 |
| `Guide` | 自研 | 新手引导（遮罩/镂空/气泡定位求解），**带单测** |
| `Terracotta` | **第三方 AGPL-3.0** | 联机隧道（VPN 服务） |

> **值得学的形状**：把「状态机 + 几何/手势求解」这类最难的 UI 逻辑**抽成无 UI 依赖的独立库并加单测**，只留最薄的 UI 层在 App 里。这恰好是 WebView 方案最难迁移的部分——先分层，再做 UI 栈决策。

### 16.3 启动编排：阶段化任务流水线

链路顺序（`Kotlin 侧`）：

`SplashActivity`（组件解包）→ `MainActivity`（Compose 主界面）→ 用户点启动 → `LaunchGameViewModel` → **`GameLaunchFlow.launch`** → `VMActivity`（渲染宿主，拉起前台服务）→ Surface 就绪 → `GameHandler.execute` → `GameLauncher.launch` → `Launcher.launchJvm` → `VMLauncher.launchJVM`（进 JVM）。

**最有价值的一处设计**：`GameLaunchFlow` 把启动前置做成**「带标题、可取消、可观察」的任务流水线**（`GameLaunchFlow.kt:103-221`）：

1. 联网检测 → 2.（可选）账号校验/刷新 → 3. 扫模组并打补丁 → 4. 游戏完整性校验与修复 → 5. 进 JVM

对外只暴露一个状态流给 UI 渲染任务列表；错误按异常类型分流到不同对话框（需要重登 / 校验失败）。**比 FCL 的"一串前置检查函数"更好用**——UI 能实时显示"正在校验文件 37%"。

关键类职责：`GameLauncher`（JVM 参数装配、JRE 选择、渲染器环境变量、工作目录、日志路径）、`LaunchArgs`（参数与变量表替换）、`GameHandler`/`JVMHandler`（"跑游戏"与"跑 jar"两种策略）、`ZLBridge`/`NativeLibraryLoader`（JNI 门面）。

**JRE 选择**：实例级指定优先 → 否则看全局设置 → 若开自动，按清单里的 Java 主版本推目标版本，再取"最近可用版本"。JRE 用枚举描述（内部 8/17/21/25），首次使用时解包。

### 16.4 原生层：30 个 C 文件、11 个 so

用 `Android.mk` 编出 **11 个 `.so`**：`pojavexec`、`vulkan_check`、`exithook`、`driver_helper`、`linkerhook`、`pojavexec_awt`、`awt_headless`、`awt_xawt`、`flite`、`fliteWrapper`、`flite_cmu_us_kal16`。

要点：

- **`.so` 依赖链比 FCL 扁平**：没有 FCL 那层中间的 `fcl` 库，JNI 入口直接并进 `pojavexec`。
- `linkerhook` 同样强制 `-z global`；`pojavexec` 用 `-rdynamic` 导出符号。
- **arm64 条件编译**：三处按 ABI 追加 Adreno 相关宏（必要的还链 EGL/GLESv2）。
- `Application.mk` 固定平台为 **android-21**、STL 为 `c++_shared`；ABI 由 Gradle 参数 + 分包决定。
- bytehook 经 **prefab** 导入。

**与 FCL 的原生层增删（这条对自研很有用——它告诉我们哪些模块是"可选的"）**：

| Zalith 有而 FCL 没有 | 价值判断 |
|---|---|
| `vulkan_checker.c`（Vulkan 能力探测 + 日志回调） | **值得做**：花小钱换"驱动兼容问题能定位" |
| `exit_hook.c` / `sdl_hook.c` / `sdl_dlopen_hook.c`（SDL3 集成） | 手上无手柄 SDL 需求可先不做 |
| `bigcoreaffinity.c`（绑大核 + 频率扫描） | **值得做**：手机上性能/发热敏感 |
| `logger/`（统一原生日志） | **值得做**：跨 JVM 排查的命脉 |
| `driver_helper` 独立成 so | 可选（FCL 并进主库） |
| `flite/*`（TTS）★ | ❌ **不要碰**：文件头自述来自 FCL 的 PR，GPL-3.0 |
| `ctxbridges/br_loader.c`（符号加载器） | 与 FCL 的 loader 同类 |
| `ctxbridges/virgl_bridge.c` | 与 FCL 的 virgl 实现同类 |

| FCL 有而 Zalith 没有 | 说明 |
|---|---|
| `fcl_bridge.c` / `fcl_loader.c` | 中间库设计差异，非能力差异 |
| `jvm_hooks/emui_iterator_fix_hook.c` | 华为旧固件补丁——**说明这类厂商补丁是可选的**，遇到再加 |
| `awt_headless/placeholder.c` | Zalith 的 `awt_headless` 干脆是**无源文件的空库** |

### 16.5 LWJGL 补丁策略（本次最有价值的收获）

**做法：在官方 jar 之上叠一层「同 FQCN 的覆盖类」，再合并成一个 fat jar。**

- 官方 jar 放各版本模块的 `libs/<版本>/`。
- 模块自身源码里放**同名同类**的覆盖类；构建时用 `zipTree` 把官方 jar 展开合并，`duplicatesStrategy = EXCLUDE`，于是**模块自己的类覆盖官方同名类**。
- 一组"不参与合并、只旁路复制"的模块单列（`excludedModules`），原样拷到产物目录。
- 输出到 App 资产目录；`version` 文件用**产物内容的 SHA-1**（不是时间戳）作为解包缓存判据。
- 两个版本各自一个模块，**公共代码抽到 `shared`**（改一处、两版本同时生效，且必须保持 Java 8 兼容）。

**覆盖面就是补丁面**，按功能只有 6 类（约 20 个同名类）：

| 类别 | 覆盖了什么 |
|---|---|
| 窗口/平台伪造 | GLFW 主类（约 1600 行）、窗口属性、回调容器 |
| 平台 native 桩 | X11 / Wayland / Win32 / Cocoa / NSGL / WGL / EGL / OSMesa 八个绑定类降级为"调用即抛" |
| 回调桥 | 输入/剪贴板/光标形状的 native 声明 |
| GL 能力初始化 | 生成的能力类 + 渲染器初始化钩子（按库名判定 gl4es 并做内部初始化） |
| JDK/ART 适配 | 内存映射工具组（`org.lwjgl.util.mapped.*`）+ **内联的 Android `ArrayMap` 等容器类** |
| 仅 3.4.1 | SDL 初始化与鼠标绑定 |

**为什么这套比 FCL 更值得学**：补丁面 = 约 20 个同名类 + 一个共享目录，升级官方 LWJGL 时只需**重新对齐这批类**，不需要维护一整棵 fork 的树。FCL 是同一套思路的早期版本（目录布局、排除清单、合并写法都被 Zalith 继承），Zalith 补上了「跨版本共享」与「内容哈希缓存」两块。

### 16.6 渲染器：Kotlin 虚接口 + C 函数表 + 插件化

- **Kotlin 侧**：一个渲染器接口描述"渲染器需要的环境变量、要 dlopen 的库、EGL 库名"等；一个注册表维护内置渲染器。
- **内置 6 个**：NG-GL4ES、GL4ES、Kopper-Zink、VirGL、Freedreno、**Panfrost**（比 FCL 去掉 VGPU、新增 Panfrost）。
- **C 侧**：一张上下文函数表（初始化 / 建上下文 / 切换 / 取当前 / 呈现 / 表面变更 / 垂直同步）+ 通用窗口句柄，由装配函数按后端选择。
- **插件化**：渲染器、驱动、原生件、ffmpeg 均可由**外置 APK 插件**动态追加。这是 Zalith 明显比 FCL 更"可扩展"的地方——**也解释了为什么它的 driver_helper 是独立 so**。

### 16.7 输入系统：双实现分离 + 四层键码

- `InputMap` 模块 = **纯数据**（零 UI 依赖）：把 4 套编号收敛成表——Android keycode / GLFW·LWJGL 键码 / MC 键位名 / 启动器控制事件码。主模块与控件模块共用。
- **`CallbackBridge` 有两份且职责分明**：LWJGL 模块里那份**只有常量与 native 声明**（避免依赖额外 C 符号）；主模块里那份是**完整实现（约 545 行）**，热路径方法用 `@CriticalNative` 标注。这种"声明/实现分离"比 FCL 把桥混在一起更干净。
- 注入路径：物理键盘/鼠标 → 活动分发 → 忽略规则判定 → 键码转换 → 桥 → native → GLFW 回调；手柄有"UI 处理模式"与"SDL 直通模式"两条路；触摸走控件层 → 同一个桥。

### 16.8 UI 栈与状态管理（这是"UI 策略"决策的关键证据）

- **Jetpack Compose + Material 3**，**Navigation 3**（基于可序列化的导航键），Hilt 注入，ViewModel + 状态流 + Room/SQLCipher 持久化 + MMKV 轻量键值。
- **但游戏画面仍然是 `TextureView`/`SurfaceView` 宿主**，且中文输入必须走自定义 View + SDL 桥；仓库里 vendored 了一大份 SDL 的 Android 侧类（约 6400 行）。

**对「WebView 复用 Vue vs Kotlin+Compose 原生重写」的直接证据**：

| 证据 | 指向 |
|---|---|
| Compose 路线已被验证能完整跑通启动器（含设置、下载、文件管理、控件布局编辑器） | Compose 原生重写**可行**，不是理论 |
| 游戏画面必须由原生 View 承载，IME 必须原生桥 | **无论哪条路，游戏渲染面都躲不开原生**；差别只在"启动器外壳"用哪套 |
| 状态骨架（Hilt + ViewModel + 状态流 + 导航）已成体系 | 走 WebView 就要维护"Web 状态 ↔ 原生状态"的双向同步，成本随功能线性增长 |
| 真正的复杂度（输入 ~6k 行、引擎相关 ~9.2k 行）全在原生侧 | **WebView 只能省掉最表层**，省不掉难点 |

> 更新后的判断：如果 UI 只在"列表 / 表单 / 设置"，WebView+Vue 能省力；但**控件布局编辑器**（拖拽、吸附、手势、取色）这类交互是 WebView 最难受的地方，而这恰恰是启动器的核心体验之一。这一点应该计入 UI 决策。

### 16.9 实例 / 下载 / 资源平台

- **有自研核心，但不是单一 core 库**：版本清单模型与继承合并自研；**下载引擎改造自 HMCL**（下载器与抓取器的注释都注明来源）；版本号比较直接用了 HMCL 的包名（内部注明抄自 Maven 的比较实现）。
- **下载源**：默认官方；镜像支持 BMCLAPI（一整套 host→镜像替换表，改自 HMCL）与 MCIM；用户可选 自动/官方/镜像。
- **覆盖面**：8 种模组加载器（Forge / NeoForge / OptiFine / Fabric / Legacy Fabric / Babric / Quilt / Cleanroom）、Modrinth + CurseForge 资源平台、4 种整合包平台（CurseForge / Modrinth / MCBBS / MultiMC）、微软 OAuth + 外置认证服务器。
- 认证还有一招：离线账号皮肤经内建的外置认证服务 + `javaagent` 注入实现。

> 对 Lumia 的意义：**这 1.5 万行"下载/资源平台"是业务代码，不是引擎**。我们的 `lumia-core` 已经把这些逻辑写好了（Rust），这是相对 Zalith 的真实优势——它得靠抄 HMCL 的算法，我们直接用自己那份。

### 16.10 构建约束（与 FCL 对照）

| 维度 | Zalith | FCL |
|---|---|---|
| 原生构建 | `Android.mk`（ndkBuild） | CMake |
| NDK | 25.2.9519653 | **27.0.12077973** |
| compileSdk | 37 | 35 |
| minSdk / targetSdk | 26 / 34（与 FCL 一致） | 26 / 34 |
| Java 级别 | app 17、库 11、LWJGL 3.3.3=**8**、3.4.1=**17** | 同样双轨 |
| Gradle / AGP / Kotlin | 9.5.0 / 9.3.0 / 2.4.20 | 8.13.2 / — / 2.4.10 |
| so 打包 | `useLegacyPackaging = true` + `pickFirsts` 收敛 bytehook | 同 |
| desugaring | 开 | 开 |
| 架构清理 | 构建后**清理非目标 ABI 的 JRE 包与 LWJGL 原生件** | 有等价处理 |

### 16.11 合规风险清单（比 FCL 更激进）

- 全盘存储权限（含两个 legacy 开关）；关闭 native 堆指针标记（为 native hook 让路）。
- **多进程**：游戏进程、JVM 服务进程、文件管理进程各自独立。
- **三个 specialUse 前台服务** + 一个 VPN 服务（联机）。
- 录音权限 + 高采样率传感器（陀螺仪）。
- 声明依赖**外部 ffmpeg 应用**（靠另一个 App 提供 ffmpeg）。

### 16.12 工程量：引擎只占 7~8%

| 范围 | 行数 |
|---|---|
| 全仓 .kt/.java | **211,838** |
| ├ UI | 77,199 |
| ├ 文件管理 | 15,629 |
| ├ 下载/资源平台/整合包 | 14,916 |
| └ **引擎相关**（launch + input + bridge + renderer + components + plugin 等） | **9,207** |
| 原生层（含 vendored 数据表与 GL 头） | 21,039（去掉 vendored 后自研约 6~8k） |
| LayerController / CardGrid / Guide / ColorPicker / InputMap | 合计约 15.8k |

**结论**：真正的引擎总量约 **1.5~1.7 万行**，占全仓 **7~8%**；其余 92% 是产品功能。这与 FCL 的画像一致——**引擎是稀缺但不大的一块，外围才是工作量大头**。

### 16.13 值得学的 5 个设计

1. **LWJGL 补丁面共享化 + 内容哈希缓存**：补丁 = 一层同名类覆盖，公共修复进 `shared`，缓存键用内容哈希。升级官方库只需重新对齐覆盖类。
2. **渲染后端的双层抽象**：Kotlin 侧虚接口描述"需要什么"，C 侧函数表描述"怎么做"，新增后端只实现函数表、不改上层。
3. **多进程切分 + 前台服务分层保活**：从第一天就把游戏进程与启动器 UI 进程隔离，游戏崩溃不拖垮启动器。
4. **启动流程阶段化任务流水线**：前置检查模型化为"可取消、可观察、带标题"的任务，UI 直接渲染进度与错误分流。
5. **复杂 UI 逻辑外溢成无 UI 依赖的库并加单测**：控件布局模型、网格布局、取色、引导定位——先分层，再做栈决策。

## 十七、两套实现对照：同一条链路，各自怎么解

| 环节 | FCL 的做法 | Zalith 的做法 | 自研取谁 |
|---|---|---|---|
| 工程组织 | 单 app + 少量库 | 1 app + 7 库，通用 UI 抽库并单测 | **Zalith** |
| 原生构建 | CMake | `Android.mk` | 无所谓，选 CMake（可读性更好） |
| 原生分层 | 多一层中间 so | 链路更扁平，驱动/探测器独立 so | **Zalith**（探测与日志独立） |
| JVM 启动 | 走 `JLI_Launch` 等价路径 | 同 | 一致，按同一机制实现 |
| JRE | 4 套 xz 分包，目录固定 | 同思路，枚举描述 + 首次解包 | 一致 |
| 渲染后端 | 固定常量集，后端最多 | 注册表 + **APK 插件可扩展**，新增 Panfrost | **Zalith 的接口形状**，但第一版只做 2 个后端 |
| 上下文抽象 | C 函数表 | Kotlin 虚接口 + C 函数表 | **Zalith**（双层） |
| 输入 | 键码表留在主模块 | `InputMap` 独立成零依赖模块 | **Zalith** |
| 桥实现 | 混合 | 声明与实现分离，热路径标注 | **Zalith** |
| LWJGL 补丁 | 整份 fork 式重编 | **同名类覆盖 + 合并 fat jar + 内容哈希** | **Zalith**（维护成本低一个量级） |
| 启动前置 | 一串检查函数 | **阶段化任务流水线** | **Zalith** |
| UI 栈 | XML + View binding | **Compose + Navigation3 + Hilt** | 取决于 UI 决策（见 16.8） |
| 启动器核心 | 源自 HMCL 的 core | 自研 + 抄 HMCL 的下载算法 | **都不取**——我们有 `lumia-core` |
| 驱动绕行 | 有（arm64 专属） | 有（且做成独立 so + 插件） | 先不做，列为 M0 验收项 |
| 厂商补丁 | 有（华为 EMUI 死锁修复） | 无 | 先不做，遇到再加 |

**一句话**：**引擎机制看 FCL（原生层最全、注释最详），工程结构与可维护性看 Zalith（分层、共享、缓存、流水线都更现代）。**

## 十八、对 Lumia 安卓端（方案 ①-B）的结论

### 18.1 体量判断（两个独立样本互相印证）

| | FCL | Zalith | 结论 |
|---|---|---|---|
| 引擎相关自研代码 | 编排层 ~3k 行 + 原生层 ~4k 行 | 引擎胶水 9.2k 行 + 原生自研 ~6~8k 行 | **1.5 万行量级**，不是"重写到天荒地老" |
| 引擎占全仓比例 | 少数 | **7~8%** | 92% 是产品功能 |
| 外围大头 | 模组/整合包/联机生态 | UI 77k、文件管理 15.6k、下载 14.9k | **我们的 `lumia-core` 已覆盖下载/实例这块**，等于开局领先 |

### 18.2 三块硬骨头可以先绕

1. **私有驱动绕行（Turnip/命名空间）** → 先只做"系统驱动 + ANGLE/GL4ES"，把**"是否需要私有驱动"列为 M0 明确验收项**。两家都做了，但都把它做成独立模块——说明它是**可选插件**而不是必选路径。
2. **AWT** → 第一版不做（不支持 MC 自带安装器与 Swing 界面）。Zalith 的 `awt_headless` 干脆是空库，印证"占位即可"。
3. **多渲染后端** → 第一版只做 GL4ES + OSMesa（一个能用、一个兜底），其余留接口位；接口形状照 Zalith 的"Kotlin 虚接口 + C 函数表"双层。

### 18.3 必须照做的"形状"（可自行命名与实现）

- 路径单一事实来源（所有运行时路径集中注册）
- 跨 `dlopen` 边界的全局单例（环境变量存指针 + 构造期取/建）
- 上下文桥函数表：初始化 / 建上下文 / 切换 / 取当前 / 呈现 / 表面变更 / 垂直同步（**7 项**）
- 键码的**分层**映射（Android → GLFW → MC 绑定名 → 启动器事件码），且这层必须零 UI 依赖、可单测
- 输入事件"队列模式 / 直调模式"双开关
- 启 JVM 前重置信号表（`SIGSEGV` 用忽略）
- 游戏进程与启动器 UI 进程**从第一天就隔离**
- 启动前置做成"可取消、可观察、带标题"的任务流水线

### 18.4 必须回答的三个外部假设

1. Vulkan 如何加载（是否需要绕命名空间/替换驱动）
2. 子进程能力如何替代（`xdg-open`、`ffmpeg` 这类在 Android 上不存在的调用）
3. 厂商固件缺陷如何规避（华为旧固件的链接器死锁是已知案例）

### 18.5 两家共有的"既成事实"（自研必须遵守）

- minSdk 26、targetSdk 34；**LWJGL 3.3.3 必须 Java 8 工具链、3.4.1 必须 Java 17**
- so 必须 `useLegacyPackaging = true`（否则 `dlopen` 出问题）
- 必须关闭 native 堆指针标记（否则与 hook 冲突）
- 必须按目标 ABI 清理资产，否则 APK 爆炸
- 只有 arm64 才有的路径（私有驱动、Adreno 特判）必须条件编译
- 全盘存储权限 + 多进程 + 前台服务 → **上架 Google Play 基本无望**，走官网/GitHub/F-Droid

### 18.6 许可证纪律（本笔记存在的理由）

- 参考对象均为 **GPL-3.0**；Zalith 还额外引入 **AGPL-3.0 的 Terracotta**、并把来自 FCL 的 GPL 代码（TTS 模块）也带了进来。**越是"功能全"的实现，许可证越脏**——这反而是自研路线的一个额外优势。
- 本笔记只留"做什么 / 为什么 / 有什么坑"，不留"怎么写"。**每个模块动工前先在此写下接口与流程，再离开参考源码独立实现。**

## 附录、如何低成本拿到参考源码

Zalith 仓库 **773 MB**（预编译二进制为主），普通 `git clone --depth 1` 实测 15 分钟才下 50 MB（GitHub 直连被限速）。可行做法：

1. 先查体积：`GET https://api.github.com/repos/<owner>/<repo>` 看 `size` 字段（单位 KB）。
2. 大仓库用 **blob 过滤 + 不检出**先拿元数据（秒级完成）：
   `git clone --depth 1 --single-branch --filter=blob:none --no-checkout <url> <dir>`
3. 列出文件树并按扩展名筛出文本源码（排除 `.so/.aar/.jar/.xz/.png`），生成 pattern 列表；
   `git ls-tree -r --name-only HEAD | grep -E '\.(kt|java|c|h|xml|kts|toml|md)$' > /tmp/pat.txt`
4. 非 cone 模式稀疏检出这些文件：`git sparse-checkout set --no-cone $(cat /tmp/pat.txt)`
   然后 `git checkout` —— 只按需拉取这些 blob。
5. 结果：**22 MB / 909 个源文件**，几分钟内可用，二进制一个没下。

> 这套流程对「只想读代码做技术参考」的场景是通用的，尤其适合动辄几百 MB 的 Android 项目。
