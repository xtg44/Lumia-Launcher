# Crystal Launcher 安卓端实施规划

> 状态：规划稿，待决策 · 编写日期：2026-10-31
> 基线：桌面端 v1.0.0（commit `e5d9604`，含版本管理二级侧边栏）
> 关联文档：[安卓端技术方案](./安卓端技术方案.md)（引擎与许可证调研） · [引擎参考笔记](./安卓端引擎参考笔记.md)（JNI 各层拆解） · [插件系统设计](./插件系统设计.md) · [前端开发指南](./前端开发指南.md)
>
> 本文只解决两件事：**路线怎么选**、**从现有代码出发要动哪里、按什么顺序动**。引擎内部实现细节不在这里重复。

---

## 一、先给结论

| 问题 | 结论 |
|---|---|
| 安卓端做不做成「桌面端编译到手机」？ | **不能。** 桌面端启动链是 `java` 命令行 + 系统 JRE + 桌面 OpenGL；Android 三样都没有 |
| 最合理的形态？ | **原生外壳 + 共用 Rust 核心 + 复用桌面端已调研的 JNI 引擎**（路线 C） |
| UI 用什么？ | 游戏外的界面 **Kotlin + Compose 重写**；不建议把 24 个 Vue 组件整体塞进 WebView |
| 先做什么？ | **先拆 `crystal-core`**（不管最终走哪条路，桌面端都受益），再做 M0 真机引擎验证 |
| 一个人多久能用？ | M0 验证 1~2 天；能用 beta **3~5 个月**；上架级 **6~9 个月** |
| 最大风险 | 不是技术选型，是 **GPU 驱动兼容** 与 **许可证分层** |

## 二、三条路线对比

### 路线 A · 伴侣 / 遥控端（Companion）

手机只做「管理 + 遥控」，游戏仍在电脑上跑。

- 能做：实例列表、下载/更新排队、远程启动、日志/截图查看、联机房间管理
- 技术：Tauri 2 Android 或 Compose + HTTP/WebSocket，复用 `crystal-core` 的清单与下载逻辑
- 工期：**3~4 周**可出可用版本
- 价值：留存/多端协同，但**不满足「手机上玩 Java 版」的核心诉求**

### 路线 B · 云端串流客户端

手机是薄客户端，渲染在服务器/PC 上。

- 技术：Moonlight / 自建 WebRTC + 编码管线；延迟与带宽是硬门槛
- 工期：客户端 4~6 周，**服务端与带宽成本是长期负担**
- 价值：低端机也能玩，但把「免费开源启动器」变成「需要持续付费的服务」

### 路线 C · 本地独立运行时（Pojav 系）

手机本地跑 OpenJDK + 图形翻译层，真正启动 Java 版。

- 技术：Kotlin/Compose 外壳 + `crystal-core`(Rust cdylib) + Amethyst 系 JNI 引擎 + 自带 JRE
- 工期：beta 3~5 个月（详见第六节）
- 风险：驱动兼容、发热续航、LGPL-3.0 分层
- 价值：**唯一能满足「Crystal 在手机上启动 MC」的路线**，也是同类产品已验证可行的路线

### 推荐

> **以 C 为主线，把 A 当作 M1 的副产品。**
>
> 理由：A 的能力（实例管理、下载队列、日志）本来就是 C 的前置模块；先按 C 拆架构，M1 阶段顺手就能拿出 A 形态的可用包，用来提前验证登录/下载/UI 手感，不至于 3 个月没有任何可交付物。B 不作为产品方向，最多作为后期「低配兜底」实验。

## 三、目标架构（在现有代码上落地）

```
┌─────────────────────────────────────────────────────────┐
│ Android App（Kotlin + Compose）                          │
│  Compose UI · 前台下载服务 · SAF/存储 · 通知 · 权限        │
├──────────────────────────┬──────────────────────────────┤
│ crystal-core（Rust cdylib） │ 引擎层（C + JNI，来自基线）     │
│  版本清单 · BMCLAPI 下载  │  jre_launcher · egl_bridge     │
│  Mod/整合包/资源包        │  input_bridge · awt_bridge     │
│  auth.rs 设备码登录       │  jvm_hooks · nsbypass          │
│  lumi.rs 解释器           │  图形翻译层（GL4ES/ANGLE/…）    │
├──────────────────────────┴──────────────────────────────┤
│ Android 运行时：libjvm.so · SurfaceView · OpenAL · 触摸    │
└─────────────────────────────────────────────────────────┘
```

**关键约束**：`crystal-core` 不依赖 `tauri`、不依赖 `std::process`、不假设桌面路径——它是桌面端和安卓端唯一共享的代码面。

## 四、现有仓库改造清单

桌面端现状（实测）：`src-tauri/src` 共 **14,448 行**，其中 `main.rs` **10,305 行**；**78 个** `#[tauri::command]`（main 65 / plugins 8 / music 5）；`Command::new` **11 处**；`cfg(target_os)` **14 处**；**没有 `lib.rs`**，全部逻辑绑在 binary 里；前端 **24 个 Vue 组件**。

### P0 · 拆 `crystal-core`（安卓前置条件，桌面端同步受益）

| 动作 | 说明 |
|---|---|
| 新建 `crates/crystal-core` | 纯 lib crate，`cargo test` 可直接覆盖 |
| 迁入纯逻辑 | 版本清单解析、BMCLAPI 多源下载（含分片/重试/校验）、Modrinth/CurseForge 查询、整合包/Mod/资源包解包、`auth.rs` 设备码登录、`lumi.rs` 解释器 |
| 定义 `CrystalPaths` 抽象 | 现在路径散落在 `main.rs`（`app_data_dir()` 等），改为构造期注入根目录，桌面传 `$DATA/Crystal`，安卓传 app 私有目录 |
| 进度回调用 trait / channel | 现在大量 `window.emit(...)` 直连 Tauri，改成 `ProgressSink`，桌面用 Tauri 实现、安卓用 JNI 回调 |
| 生成 Kotlin 绑定 | **uniffi**，一处 `lumia.udl`，两端共用；避免手写 78 个 JNI 函数 |
| 桌面端退化 | `main.rs` 只保留「window / 菜单 / 快捷键 / 文件名」薄壳，命令转发 core；验收标准是桌面端行为零变化 |

> 这一步工作量大（`main.rs` 10k 行切分，预计 **2~3 周**），但它是「一份业务逻辑，两个端」的唯一前提；不做则安卓端只能复制粘贴一份 Rust，之后必然分叉。

### P1 · 平台门控（`cfg(desktop)`）

| 位置 | 现状 | 处理 |
|---|---|---|
| Java 检测/启动（9 类逻辑，`get_java_path_from_env`、`collect_java_paths`、`choose_java_exec`…） | 扫描 `JAVA_HOME`、全盘找 `java` | 整个模块 `#[cfg(desktop)]`；安卓走「内置 JRE + 进程内 JVM」 |
| `Command::new`（11 处） | Forge/NeoForge 安装器、`taskkill`/`pkill`、外部程序 | `#[cfg(desktop)]`；安卓改为进程内调用或 Kotlin 侧实现 |
| `open` crate / `tauri-plugin-opener` | 打开文件夹、外部链接 | 桌面保留；安卓换 `Intent` / SAF |
| `touchbar.rs`（305 行） | macOS | 仅 macOS 编译 |
| `updater.rs`（893 行） | 自研桌面更新（替换自身二进制） | 安卓换 APK 内更新（`PackageInstaller` + 签名校验） |
| 窗口配置 | 900×600、无边框、`transparent`、`shadow:false` | 桌面专属；安卓不加载该窗口配置 |
| 自定义协议 `stream://`、`asset://` | 音乐流式播放、本地图片 | 安卓换 ExoPlayer + 直接 `File`/`content://` |

**做法**：新增 `#[cfg(desktop)] mod desktop;` 把上述内容装进一个模块，而不是在 10k 行里撒 `cfg`。目标：`cargo check --target aarch64-linux-android` 能过。

### P2 · 移动端特有改造

| 主题 | 方案 |
|---|---|
| 存储 | 游戏目录放 app 私有目录（免权限）；导入/导出走 SAF；`MANAGE_EXTERNAL_STORAGE` 只在「自定义目录」场景申请 |
| 下载 | `ForegroundService` + 通知进度；锁屏/切后台不断；Wi-Fi Only、并发数、断点续传沿用 core |
| 登录 | 设备码流程（`auth.rs` 已具备，无需本地回调端口），Compose 里做二维码/验证码页 |
| 崩溃上报 | 现有 `CrashReport.vue` 逻辑 → 原生崩溃捕获 + 同一后端接口 |
| 插件 | Lumi 解释器可复用；宿主 `plugins.rs` 的控件树需映射到 Compose（`PluginPage`/`PluginInject` 两页对应重写） |
| 音乐 | `music.rs` 曲库逻辑复用，播放器换 Media3/ExoPlayer |
| 联机 | Terracotta 换 arm64 二进制或走官方 HTTP API；房间页重做 |

## 五、移动端 UI 方案

桌面端的辨识度来自：60px 竖向图标栏、选中指示块、卡片化列表、无可见滚动条。安卓端**保留语言，改变形态**。

### 5.1 外壳

| 桌面端 | 安卓端 |
|---|---|
| 左侧 60px 竖向导航（首页/下载/版本/联机/音乐/插件/设置） | **底部导航 5 项**（首页 / 下载 / 版本 / 联机 / 更多）；设置、插件、音乐、AI 收进「更多」 |
| 顶部自绘标题栏（关闭/最小化） | 系统状态栏 + 安全区 `WindowInsets`；无自绘标题栏 |
| 选中指示块 `translateY` | 选中态改为**图标填充 + 文字加粗 + 底部小圆点**，去掉滑动指示块（触屏无 hover，位移感反而慢） |
| 900×600 固定窗口 | 手机竖屏为主（390~430dp），平板/横屏 600dp+ 时切换为 **NavigationRail** |

### 5.2 版本管理（本次刚改完的界面）

| 桌面端 | 安卓端 |
|---|---|
| 二级竖向 `section-nav`（60px，4 个 tab） | **顶部横向 Chips**：概览 / 模组 / 截图 / 其他，可滑动，选中填充主色 |
| 概览卡片 + 右侧操作 | 单列卡片，操作收进右上 `⋮` 或底部按钮 |
| 模组列表（表格 + 开关） | 两行列表项：名称/版本 + 右侧 Switch；搜索固定在顶部 |
| 截图懒加载网格 + 灯箱 | 3 列网格 + 全屏 `Pager`（左右滑动切换） |
| `.mrpack` 导出 | 走 SAF「另存为」，显示前台通知进度 |
| 危险操作二次确认 | 底部 `ModalBottomSheet` 确认，红字按钮 |
| 悬浮返回箭头 | 系统返回手势 + 顶部 `TopAppBar` 返回 |

### 5.3 通用规范

- 触控目标 ≥ **48dp**，列表项高 ≥ 64dp；桌面端 hover 效果全部改为 press/ripple
- 字号：正文 14sp、次要 12sp、标题 20sp；桌面端 10px 小字**不可直接搬**
- 无可见滚动条保留（Compose 默认即是），但列表要有 overscroll 反馈
- 深色/浅色跟随系统 + 手动覆盖，与桌面端主题变量对齐（同一套色值）
- 游戏内：横屏 + 沉浸式全屏 + 虚拟按键层（移动/视角/跳跃/背包），退出用悬浮球
- 动效：桌面端 `cubic-bezier(0.34,1.2,0.64,1)` 的弹性曲线可用 `spring` 近似，但幅度减半

### 5.4 24 个组件的去向

| 组件 | 去向 |
|---|---|
| Home / Download / VersionSelector / VersionManage / Mod / ResourcePack / ShaderPack / Settings | Compose 重写（核心 8 页） |
| DownloadDetail / DownloadConfig / ModpackInstallModal | 合并为「下载任务详情」+ 配置底部弹层 |
| Music + PlayerBar | Media3 + 底部迷你播放条 |
| Terracotta | 重写（服务端能力不变） |
| PluginCenter / PluginPage / PluginInject | 重写，控件树映射 Compose |
| AiAssistant | 保留，改为全屏对话页（可后置） |
| CrashReport / UpdateModal / WhatsNew / ConfirmHost / ToastHost / AppSelect | 系统级能力替代（通知、Dialog、Snackbar） |

> **不建议**用 WebView 复用 Vue：WebView 与游戏 `SurfaceView` 的合成、手势冲突、返回键、输入法都要额外打补丁，省下的 UI 工作量会在集成阶段还回去。

## 六、里程碑与验收

| 阶段 | 内容 | 工期 | 验收标准 |
|---|---|---|---|
| **M0** | 环境补齐（NDK/cmdline-tools/adb），编译 Amethyst 基线，真机跑 MC 1.20.x | 1~2 天 | 进入世界，记录帧率/渲染器/崩溃日志/最高可跑版本 |
| **M0.5** | 抽 `crates/crystal-core` + uniffi 绑定，桌面端零回归 | 2~3 周 | 桌面端功能与测试全绿；`cargo check --target aarch64-linux-android` 通过 |
| **M1** | 新仓库骨架：包名/图标/主题/底部导航；登录 → 选版本 → 启动 最小闭环 | 2~3 周 | 真机走通一次完整启动，含下载与 JRE 装配 |
| **M1.5** | 「伴侣形态」可交付包（实例管理 + 下载队列 + 日志），可作为 A 路线提前发布 | 1~2 周 | 与桌面端共用下载逻辑，任务可持续后台 |
| **M2** | 接入 core：版本清单、BMCLAPI 多源、Mod/整合包/资源包 | 3~4 周 | 与桌面端下载结果逐字节一致（同 sha1） |
| **M3** | 版本管理四页（概览/模组/截图/其他）+ 设置 | 2~3 周 | 对齐桌面端 `VersionManageView` 能力 |
| **M4** | Lumi 插件系统 + 联机 + 音乐 | 4~6 周 | 插件能注册页面并响应事件；房间可创建/加入 |
| **M5** | 性能与兼容打磨、多语言、APK 更新、发布 | 3~4 周 | 3 档机型（低/中/旗舰）稳定 30fps+；签名 APK 可自更新 |

**并行建议**：M0 与 M0.5 由同一人顺序做（先 M0，1~2 天换掉最大未知数）；M1 起可并行 UI 与 core 接入。

## 七、风险与合规

| 风险 | 等级 | 应对 |
|---|---|---|
| GPU 驱动兼容（Mali/Adreno/PowerVR 差异） | 🔴 高 | 机型测试矩阵；保留 OSMesa 软件渲染兜底；开屏标注最低配置 |
| 发热/续航/性能天花板 | 🔴 高 | 渲染距离/分辨率缩放预设；不承诺与 PC 同体验 |
| 许可证分层（Amethyst LGPL-3.0 vs 本项目 MIT） | 🟡 中 | **独立仓库**；LGPL 部分动态链接、附源码与许可声明；正式发布前咨询律师 |
| Google Play「下载并执行代码」政策 | 🟡 中 | 主渠道 GitHub / 官网 APK / F-Droid；Play 版可考虑裁剪为路线 A |
| 上游停更（Pojav 已归档，Amethyst 为继任者） | 🟡 中 | 锁定可编译 commit；关键补丁在自有 fork 内维护 |
| `main.rs` 拆分引入回归 | 🟡 中 | 先补测试再移动代码；按模块小步提交，桌面端每次 release 前跑全量 |
| 移动端包体（JRE 三套 ~154MB） | 🟢 低 | 按需下载 JRE（首次启动时选择），APK 只带 arm64 最小集 |

## 八、决策点（开工前需确认）

1. **路线**：确认以 C 为主线、A 作为 M1.5 副产品？还是先只做 A？
2. **仓库**：确认新建 `Crystal-Launcher-Android` 独立仓库（推荐，隔离许可证），还是在当前仓库开 `android/`？
3. **引擎基线**：①-A 复用 Amethyst（LGPL，快）还是 ①-B 全自研 JNI（纯 MIT，慢 3 倍）？
4. **ABI**：只发 `arm64-v8a`（覆盖 95%+ 新机，包体最小）还是加 `armeabi-v7a`？
5. **首发渠道**：官网 APK / GitHub Releases / F-Droid / Play（影响是否要裁功能）？
6. **M0 机型**：先用哪台真机验证（决定后续测试矩阵的基线）？

> 建议顺序：**先批 M0（1~2 天）+ M0.5（2~3 周）**，其余决策可在 M0 拿到真机数据后再定。
