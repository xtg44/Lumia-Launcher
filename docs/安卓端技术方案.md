## 二、为什么难：四条硬约束

桌面端的启动链路是「拼一条 `java` 命令行 → 交给操作系统执行」。在 Android 上，这条链路的每一环都断了：

| # | 桌面端做法 | Android 现实 | Lumia 现有代码 |
|---|---|---|---|
| 1 | 用系统 JRE（`JAVA_HOME` → 全盘找 `java`） | **没有系统 JRE**，必须自带并随包分发（OpenJDK 8/17/21，三套并存 ~154 MB） | `main.rs` 中 9 处 java 检测/启动逻辑**整块作废** |
| 2 | `Command::new(java)` 起子进程 | Android 10+ **禁止执行应用私有目录里的文件**，且无 `taskkill`/`pkill` | 13 处 `Command::new` 全部作废 |
| 3 | 直接用桌面 OpenGL 3.2+ | 只有 GLES / Vulkan，需**图形翻译层**（GL4ES / ANGLE / OSMesa / VirGL / Zink） | 无影响（但这是引擎最大的一块） |
| 4 | Tauri 2 + Vue 桌面窗口 | Tauri 2 的 Android 支持虽已 GA，但**原生渲染面与 webview 合成在移动端仍不成熟** | 不适合承载游戏渲染面 |

> **结论**：Android 端不是「把 Lumia 编译到手机上」，而是**换一套引擎、复用一部分业务逻辑**。

## 三、基线选择

### 3.1 生态现状（2026-09 实测）

```
Boardwalk (2013, 已死)
    └── PojavLauncher (LGPL-3.0, 9393★)  ← 2025-09 官方归档 ⚠️
            ├── Amethyst-Android (LGPL-3.0, 2211★)  ← 官方继任者，活跃 ✅
            │       └── Amethyst-iOS (GPL-3.0, 1469★)
            ├── ZalithLauncher2 (GPL-3.0, 1897★, Kotlin)  ← 现代 UI 分支
            └── FoldCraftLauncher (GPL-3.0, 4787★)        ← 国内主流，功能最全
```

### 3.2 许可证矩阵（GitHub API 实测）

| 组件 | 许可证 | 可否用于 MIT 项目 | 说明 |
|---|---|---|---|
| **Amethyst-Android** | **LGPL-3.0** | ✅ **可作基线** | 动态链接场景下，自有代码可保持 MIT |
| PojavLauncher | LGPL-3.0 | ⚠️ | 已归档，不建议新项目依赖 |
| ZalithLauncher2 | GPL-3.0 | ❌ | 传染性，引用即整体 GPL |
| FoldCraftLauncher | GPL-3.0 | ❌ | 同上 |
| PCL2 | 无标准 SPDX | ❌ | 许可不明，不要碰 |
| OpenJDK 移动版运行时 | GPLv2 + Classpath Exception | ✅ | 作为**未修改的运行时组件**分发 |
| LWJGL3（AngelAuraMC 补丁版） | BSD-3-Clause | ✅ | Android 适配靠这个 fork |
| HolyGL4ES / gl4es | MIT | ✅ | GL→GLES 翻译 |
| ANGLE | BSD-3 | ✅ | GLES→Vulkan/GL |
| virglrenderer | MIT | ✅ | VirGL 透传 |
| OpenAL-Soft | LGPL-2.1 | ✅ | 动态链接即可 |
| GLFW | Zlib | ✅ | 引擎侧只用其 stub |

**引擎层的核心依赖全部是宽松许可**——真正带 copyleft 的只有 Amethyst 自身的编排代码（LGPL-3.0）。这给了两条路：

- **①-A 复用基线（推荐）**：fork Amethyst → APK 内含 LGPL-3.0 代码 → 自有新文件标 MIT，仓库混合许可。**工期最短。**
- **①-B 全自研引擎**：只用上表的宽松许可原生件，JNI 胶水自己写 → 可保持纯 MIT。**但 JNI 胶水约 15 个模块（见 5.3），工期 ×3 起**，且必须完全独立实现、不参考 Amethyst/FCL 源码。

> ⚠️ 许可证分层涉及法律判断，以上为工程视角的整理，正式发布前建议咨询律师。

## 四、目标架构

```
┌──────────────────────────────────────────────────────────┐
│ UI 层  （二选一，见 6.1）                                  │
│   A. Vue 3 复用 —— WebView 承载，改造成本低                │
│   B. Kotlin + Compose —— 原生手感，24 个组件全部重写        │
├──────────────────────────────────────────────────────────┤
│ Lumia 业务层（Kotlin）                                     │
│   实例管理 · 下载编排 · 账号 · 设置 · 主题                  │
├────────────────────────┬─────────────────────────────────┤
│ lumia-core（Rust cdylib）│ MC 引擎层（C + JNI）             │
│   版本清单 / BMCLAPI 下载 │   jre_launcher  · egl_bridge    │
│   Mod / 整合包 / 资源包   │   input_bridge  · awt_bridge    │
│   Lumi 解释器             │   jvm_hooks     · nsbypass      │
│   MS 设备码登录           ├─────────────────────────────────┤
│                          │ 图形翻译层                       │
│                          │   HolyGL4ES · ANGLE · OSMesa    │
│                          │   VirGL · Zink                  │
├──────────────────────────┴─────────────────────────────────┤
│ Android 运行时                                              │
│   libjvm.so（OpenJDK 8/17/21，arm64/arm32/x86/x86_64）      │
│   SurfaceView · 触摸输入桥 · OpenAL · 自定义 LWJGL           │
└────────────────────────────────────────────────────────────┘
```

**关键点**：`lumia-core` 是一层**与平台无关**的 Rust 库，桌面端和安卓端共用同一份源码。这是最大化现有投入的唯一方式。

## 五、复用矩阵

### 5.1 可直接复用（纯逻辑，无平台依赖）

| 模块 | 现有位置 | 说明 |
|---|---|---|
| 版本清单解析 | `main.rs` | 纯 HTTP + JSON |
| BMCLAPI 下载 | `main.rs`（8 个函数） | 纯网络 |
| Modrinth / CurseForge | `main.rs`（2 + 4 个函数） | 纯网络 |
| 整合包 / Mod / 资源包管理 | `main.rs` | zip/tar 解包，仅路径需改 |
| **Lumi 插件解释器** | `lumi.rs`（1530 行） | **纯 Rust，零平台依赖，可直接编成 so** |
| Microsoft 设备码登录 | `auth.rs` | 用设备码流程，**无需本地回调服务器**，移动端最省事 |

### 5.2 需改造

| 模块 | 改造点 |
|---|---|
| 插件系统宿主 `plugins.rs` | 事件模型需对接 Android 控件树，控件渲染层要重写 |
| Terracotta 联机 | 改下载 arm64 版二进制 / 走官方 HTTP API |
| 音乐播放 `music.rs` | `stream://` 自定义协议换成 ExoPlayer / MediaPlayer |

### 5.3 整块作废

| 模块 | 原因 |
|---|---|
| Java 检测与启动（9 + 13 处） | 无系统 JRE、不能 exec |
| 进程管理（taskkill / pkill） | 改为进程内 JVM |
| `touchbar.rs` | macOS 专属 |
| 桌面窗口特效 / 圆角 CSS | 无桌面窗口装饰 |

### 5.4 引擎层要自己实现的部分（若走 ①-B）

参考 FCL / ZalithLauncher2 的 `jni/` 结构（**两家均已做 clean-room 设计梳理，见 [引擎参考笔记](./安卓端引擎参考笔记.md)；GPL 代码不可参考实现**），约需：

```
jre_launcher.c        进程内启动 JVM（dlopen libjvm.so + JLI_Launch）
egl_bridge.c          Android Surface ↔ EGL ↔ MC 渲染面
input_bridge_v3.c     触摸/按键 → GLFW 事件注入
awt_bridge.c + awt_headless/ + awt_xawt/   AWT 无头化占位
jvm_hooks/            lwjgl_dlopen_hook（.so 重定向）、java_exec_hooks
driver_helper/nsbypass.c   绕开命名空间限制加载 GPU 驱动
ctxbridges/           osm_bridge（软件渲染）、loader_dlopen、swap_interval
```

再加上 LWJGL 补丁（`PojavRendererInit`、`CallbackBridge`、GLFW 各平台 stub）与整套自定义 `.so`（FCL 那边是 45 个，跨 4 个 ABI）。

## 六、待决策事项

### 6.1 UI 策略

| 方案 | 复用度 | 代价 |
|---|---|---|
| **A. WebView + Vue** | 24 个组件基本可留 | 需替换 `invoke` 通道；游戏渲染面仍需原生 Activity |
| **B. Kotlin + Compose** | 归零，全部重写 | 原生手感、无桥接层、与引擎集成最干净 |

> 不建议硬上 **Tauri 2 Android**：把游戏渲染面塞进 Tauri 的 webview 合成管线，是在框架最不成熟的地方压最重的需求。

### 6.2 许可证路线

**①-A**（fork Amethyst，APK 含 LGPL-3.0，部分文件 MIT）还是 **①-B**（全自研引擎，纯 MIT）。

### 6.3 仓库组织

建议**独立仓库** `Lumia-Launcher-Android`，与桌面端 MIT 仓库彻底分离，避免混合许可污染。

## 七、分阶段验证步骤

### M0 · 基线验证（1~2 天）★ 先做这个

目的：确认在你的目标机型上引擎确实可用，拿到真实性能数据。

环境补齐（当前机器已有 SDK 2.1 GB：platform-tools / build-tools 34,36 / platforms 34,37 / emulator；**缺 NDK 与 cmdline-tools**）：

```bash
# 1. 补 SDK 组件
sdkmanager --install "cmdline-tools;latest" "ndk;27.0.12077973"
# 2. 探真机（当前 adb 不在 PATH）
export PATH="$HOME/Library/Android/sdk/platform-tools:$PATH"
adb devices

# 3. 拉取并编译 Amethyst
git clone --recursive https://github.com/AngelAuraMC/Amethyst-Android.git
cd Amethyst-Android
./gradlew :jre_lwjgl3glfw:build
./gradlew :app_pojavlauncher:assembleDebug
adb install -r app_pojavlauncher/build/outputs/apk/debug/app-debug.apk
```

**验收标准**：手机上启动 MC 1.20.x 并进入世界，记录：帧率、渲染器选择、崩溃日志、能跑的最高版本。

### M0.5 · 抽出 `lumia-core`（桌面端同步受益）★ 第二步

**这是整件事的前提**：当前 `src-tauri` 是纯 binary，没有 `lib.rs`，56 个 `#[tauri::command]` 全绑在 8793 行的 `main.rs` 里，无法被安卓复用。

- 新建 `crates/lumia-core`（lib crate），把 5.1 表中的纯逻辑整体迁移
- 桌面端 `main.rs` 退化为薄壳，只做 tauri command ↔ core 的转发
- 用 **uniffi** 生成 Kotlin 绑定，安卓端直接调用

**收益**：桌面端也获得可测试的模块边界。这一步不管走不走安卓都值得做。

### M1 · 品牌骨架（1~2 周）

独立仓库 `Lumia-Launcher-Android`，改包名 / 图标 / 主题，UI 收敛到最小闭环：**登录 → 选版本 → 启动**。

### M2 · 接入 Rust 核心（2~4 周）

uniffi 打通后先接**下载源与版本清单**，让安卓端的下载行为与桌面端一致（同一份 BMCLAPI 逻辑）。再接 Mod / 整合包管理。

### M3 · Lumi 插件系统（4~6 周）

Lumi 解释器编进 `lumia-core`，定义 Android 控件树与事件的映射规则。

### M4 · 联机与音乐（3~4 周）

Terracotta 走 Android 版二进制；音乐换 ExoPlayer。

### M5 · 打磨与发布（2~4 周）

性能调优、驱动兼容测试矩阵、多语言、图标与启动动画。
